# 全局概念词典

> **定位**: AI 与人类协作的核心概念定义，确保双方对关键概念有共同理解
> **格式**: 定义 + 使用场景 + 示例

---

## 一、AI 协作概念

### 1. 复用（Reuse）

定义：AI 在编码过程中复用之前的编码经验和知识，不是人类程序员之间的代码复用

**使用场景**：
- AI 复用之前的编码经验
- AI 复用 skills 目录中的可复用技能
- AI 复用 experience 目录中的经验沉淀

**示例**：
```
AI：我查看了 experience/ 目录，发现可以使用构造器注入替代 @Autowired
```

### 2. 沉淀（Deposition）

定义：AI 在编码完成后，将经验沉淀到相应目录，减少后续沟通成本

**使用场景**：
- AI 将经验沉淀到 experience/ 目录
- AI 将问题记录到 issues/ 目录
- AI 将解决方案固化到规则中

**示例**：
```
AI：我已经将 LLM 集成的经验沉淀到 experience/ 中了
```

### 3. 幻觉（Hallucination）

定义：AI 生成不存在的代码或 API，或生成不符合项目架构的代码

**使用场景**：
- AI 生成不存在的代码或 API
- AI 生成不符合项目架构的代码
- AI 重复犯同样的错误

**解决**：
- 检查文档是否准确
- 检查经验沉淀是否完整
- 告诉 AI 只使用文档中提到的代码和 API

**示例**：
```
程序员：AI 生成了不存在的 API
AI：我检查了文档，发现我使用了错误的 API，现在修正
```

### 4. 500=404

定义：允许只关注能解决的问题，对于无法解决的问题，允许暂时搁置

**使用场景**：
- AI 只关注能解决的问题
- AI 遇到不能解决的问题时，允许记录后暂时跳过
- AI 快速迭代：修改本次内容，或新建独立的聚焦解决

**示例**：
```
AI：本次无法实现流式调用，我将记录到 issues/，下次迭代再实现
```

### 5. AI Rules 是圈不是线

定义：AI 遵循的规范太多，不可能全部满足，取规范集合的交集，允许按需选择

**使用场景**：
- AI 在编码前，确定本次开发的核心目标
- AI 选择与核心目标相关的规范集合
- AI 只遵循核心规范，忽略非核心规范

**示例**：
```
AI：本次核心目标是快速实现功能，我将选择规范集合：{构造器注入, Lombok}，单元测试下次补充
```

### 6. 协作内容分类

定义：目录内容按使用者分类，AI 每次行为后检查共用内容是否需要沉淀

| 分类 | 使用者 | 核心特征 | 典型文件 |
|------|--------|---------|---------|
| AI 专用 | AI | 跨 AI 模型可用、人类不需关心 | cold-start.md, *-skill.md |
| 共用 | AI + 人类 | 人类可全链路指导、追踪 AI 行为 | start.md, RULE_SPEC.md |
| 人类专用 | 人类 | 简单明了、程序员间沟通 | 需求冷启动.md, 产品需求.md |

**判断方法**：
```
问：这个文件谁会主动打开阅读？
答：只有 AI 打开 → AI 专用
答：AI 和人类都会打开 → 共用
答：只有人类打开 → 人类专用
```

## 二、执行模式概念

### 7. 工作流模式 vs 对话模式

定义：两种不同的 LLM 使用场景，需要不同的配置和行为

| 模式 | 时效性检查 | 上下文 | 典型场景 |
|------|-----------|--------|---------|
| 工作流模式 | 不需要 | 固定 | 报告生成、数据处理流程 |
| 对话模式 | 需要 | 动态 | 智能客服、对话机器人 |

**使用场景**：
- 工作流模式：固定流程、无需时效性、批量处理
- 对话模式：动态交互、需要时效性、实时响应

### 8. 节点上下文依赖

定义：工作流节点之间的数据传递和依赖关系，每个节点需要明确输入和输出

**使用场景**：
- 节点执行时，从前置节点获取数据
- 节点执行后，向后置节点提供数据
- Prompt 模板构建时，注入上下文变量

**关键原则**：
- 明确输入：从前置节点获取什么数据
- 明确输出：向后置节点提供什么数据
- 变量定义：Prompt 模板中定义需要的变量

## 三、冷启动概念

### 9. 冷启动（Cold Start）

定义：AI 在没有上下文的情况下开始工作，需要从零理解项目结构、业务逻辑、技术栈、规范约束

**表现**：
| 表现 | 说明 |
|------|------|
| 重复询问 | 每次都要问"项目结构是什么" |
| 规范不符 | 生成的代码不符合项目规范 |
| 经验丢失 | 无法复用之前的解决方案 |
| 理解偏差 | 对需求的理解与预期不符 |

**解决方案**：详见 `.iflow/context/experience/cold-start.md`（三层防御体系）

## 四、注释规范概念

### 10. 行间注释 vs 行尾注释

定义：两种不同的注释方式，用途和规范不同

| 类型 | 格式 | 位置 | 规范 |
|------|------|------|------|
| 行间注释 | `// 注释内容` | 代码块之前，独立一行 | ✅ 允许 |
| 行尾注释 | `代码; // 注释` | 代码行末尾 | ❌ 禁止 |

**使用场景**：
- 行间注释：解释业务逻辑、步骤说明、重要决策
- 行尾注释：禁止使用，应改为行间注释或 Javadoc

**示例**：
``` java
// 正确：行间注释
// 5. 异步模式：返回任务 ID
ocrTask.setTaskId(response.getTaskId());

// 错误：行尾注释（禁止）
ocrTask.setTaskId(response.getTaskId());  // 返回任务 ID
```
