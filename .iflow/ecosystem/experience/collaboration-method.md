### AI执行规范

**触发条件**：AI收到任务时，必须先查阅"触发条件索引"，确定使用哪个方法。

**输出要求**：在规划阶段显式输出"方法执行记录"，**必须列出所有方法**，对于未执行的方法说明原因。

**AI主动提出规范**：

| 触发条件 | AI必须输出 |
|---------|-----------|
| 修改多章节文档时 | 整体结构检查（内容完整性、关系正确性、顺序合理性） |
| 发现潜在问题时 | 主动提出观察和建议，不等待人类指出 |
| 方法执行前 | 输出"我理解这个方法的应用场景是...是否正确？" |
| 多个修改点时 | 使用待办列表跟踪，执行完逐项确认 |
| 规划输出前 | 元检查：是否执行所有方法？是否列出所有修改点？ |

**禁止行为**：
- 等待人类指出问题
- 只关注局部，忽略整体
- 假设现有结构合理，不质疑

**规划输出强制格式**：

``` text
## 自指检查（提出新方法/规范时必须）

**核心问题**：我是否执行了我正在提出的方法？

**执行步骤**：
1. 列出提出的新方法/规范
2. 检查自己是否执行了这个方法/规范
3. 如果没有执行，先执行，再提出
4. **终止条件**：只检查一次，检查对象是"方法内容"，不是"检查行为本身"，不递归

**协作规范传递者的角色**：
- 每次经验都需要沉淀给其他AI实例使用
- 沉淀路径：`.iflow/ecosystem/experience/`
- 沉淀内容：场景标签 + 场景描述 + 解决方案

**关键教训**：提出改进后必须落地，否则改进本身没有意义。

**重要**：例子不能保证执行，只有"多层防御"才能尽可能降低错误概率。
```

## 一、笛卡尔方法论

> **核心原理**：通过怀疑、分解、层次构建、全面检查，确保协作的确定性
> **定位**：思维层，所有其他方法的底层基础

### 1.1 四原则定义

| 原则 | 原文 | 协作应用 |
|------|------|---------|
| **怀疑精神** | 绝不承认任何事物为真，对于我完全不怀疑的事物才视为真理 | 规则理解有歧义时，质疑并验证 |
| **分解原则** | 必须将每个问题分成若干个简单的部分来处理 | 复杂问题拆分为独立模块 |
| **层次构建** | 思想必须从简单到复杂 | 从核心准则推导到具体场景 |
| **全面检查** | 我们应该时常进行彻底的检查，确保没有遗漏任何东西 | 每步输出检查表，关键操作前验证 |

### 1.2 与其他方法的关系

| 方法 | 笛卡尔原则应用 |
|------|---------------|
| **乔哈里窗** | 怀疑精神 → 质疑"是否有隐藏信息" |
| **苏格拉底提问** | 怀疑精神 → 本体与定义提问 |
| **PDCA** | 全面检查 → Check阶段验证 |
| **联动检查** | 全面检查 → 检查关联文件 |
| **流程执行要点** | 全面检查 → 关键操作前验证 |

### 1.3 错误预防案例

| 错误 | 原因 | 笛卡尔原则应用 |
|------|------|---------------|
| 规则8误解为"禁止创建md" | 未质疑自己的理解 | 怀疑精神：输出"我理解规则8是..."，等待确认 |
| endPoint.md 冗余 | 未拆分复杂问题 | 分解原则：拆分为 workflow + checkpoint |
| 检查点机制缺失 | 未从核心原则推导 | 层次构建：规则0→检查点规范 |
| 自检表不完整 | 未全面检查 | 全面检查：逐条输出规则检查结果 |
| 章节排序遗漏 | 只关注局部，未检查整体 | 全面检查：修改前检查内容、关系、顺序 |

### 1.4 强制执行

**触发条件**：
- 规则/需求理解有歧义时
- 任务涉及3个以上文件时
- 设计新的规范/目录结构时
- 任务完成自检时
- 修改多章节文档时

**执行方式**：

| 原则 | 输出要求 |
|------|---------|
| **怀疑精神** | 输出"我理解...是否正确？"，等待人类确认 |
| **分解原则** | 输出任务拆分列表，逐个执行 |
| **层次构建** | 输出层次结构，从核心到细节 |
| **全面检查** | 输出完整检查表（内容、关系、顺序），逐条确认 |

### 1.5 方法关系

| 维度 | 说明 |
|------|------|
| **所属层次** | 思维层（底层原则） |
| **下层指导** | 指导框架层（乔哈里窗）、方法层（苏格拉底/PDCA/SQ3R）、执行层（联动检查/流程要点） |
| **互补方法** | 乔哈里窗也可保证全面（识别未知区）、PDCA的Check也可保证全面 |

## 二、乔哈里窗协作模式

### 2.1 四区域定义

| 区域 | 定义 | AI协作场景 |
|------|------|-----------|
| **开放区** | 双方都知道 | rule.md、需求文档中明确记录的内容 |
| **盲点区** | 人类知道，AI不知道 | 业务背景、隐含需求、行业约束 |
| **隐藏区** | AI知道，人类没表达 | 技术细节、实现方案、潜在风险 |
| **未知区** | 双方都不知道 | 执行中才暴露的问题、边界情况 |

### 2.2 协作目标

**核心目标**：扩大开放区，缩小盲点区和隐藏区，探索未知区

### 2.3 方法关系

| 维度 | 说明 |
|------|------|
| **所属层次** | 框架层（顶层设计） |
| **上层指导** | 笛卡尔怀疑精神：质疑"是否有隐藏信息" |
| **下层应用** | 区域转化方法（三）、苏格拉底提问（四）、PDCA（五） |
| **互补方法** | 笛卡尔全面检查也可识别遗漏、乔哈里窗识别未知区可补充全面检查 |

## 四、苏格拉底提问

### 4.1 五步骤

| 步骤 | 名称 | 核心问题 | 适用区域 |
|------|------|---------|---------|
| 1 | 本体与定义 | "这究竟是什么？" | 盲点区 |
| 2 | 机制与因果 | "结果背后的动力系统是什么？" | 隐藏区 |
| 3 | 边界与约束 | "如果失败，最可能死在哪？" | 隐藏区 |
| 4 | 框架与视角 | "跨学科如何合成？" | 未知区 |
| 5 | 合成与应用 | "综合输出最终方案" | 开放区 |

### 4.2 工具选择

| 区域 | 首选工具 | 方法 |
|------|---------|------|
| 开放区 | 直接执行 | 无需提问 |
| 盲点区 | AskUserQuestionTool | 结构化确认 |
| 隐藏区 | 苏格拉底提示法 | 引导澄清 |
| 未知区 | 苏格拉底+PDCA | 探索+验证 |

### 4.3 提问示例

**本体与定义**：
``` text
普通："帮我优化这个Prompt"
苏格拉底："这个Prompt的本质目的是什么？用户真正想要什么？"
```

**边界与约束**：
``` text
普通："执行这个方案"
苏格拉底："如果方案失败，最可能是什么原因？"
```

## 五、未知区处理方案

### 5.1 方法融合

``` text
框架与视角 → 假设驱动 → PDCA验证
```

### 5.2 PDCA循环

| 阶段 | 内容 | 输出物 |
|------|------|--------|
| Plan | 提出假设/方案 | 假设陈述、方案大纲 |
| Do | 小范围执行 | 执行记录、中间结果 |
| Check | 检查结果 | 验证报告、问题清单 |
| Act | 调整改进 | 改进方案、经验沉淀 |

### 5.3 强制执行

**触发条件**：遇到未知区问题时，必须使用 PDCA 循环

**执行流程**：
1. **Plan**：明确假设，输出假设陈述
2. **Do**：小范围试错，输出执行记录
3. **Check**：验证假设，输出验证报告
4. **Act**：根据结果调整，输出改进方案

**输出物强制**：
- 每个阶段必须有输出物
- 缺少输出物视为流程未完成
- 完成后使用场景标签格式沉淀经验

## 六、SQ3R 阅读法

> **核心原理**：系统化阅读，从浏览到内化的完整流程

### 6.1 方法定义

SQ3R 是一种系统化的阅读理解方法，包含五个步骤：
- **S**urvey（浏览）：快速浏览整体结构
- **Q**uestion（提问）：提出关键问题
- **R**ead（阅读）：深入阅读关键内容
- **R**ecite（复述）：用自己的话复述
- **R**eview（复习）：回顾和巩固

### 6.2 AI 协作适配

| 步骤 | 原始含义 | AI 协作适配 | 输出 |
|------|---------|------------|------|
| **Survey** | 浏览目录和结构 | 快速扫描文件目录、import 关系 | 整体结构图 |
| **Question** | 提出阅读问题 | 识别核心类、关键方法、数据流向 | 问题列表 |
| **Read** | 深入阅读 | 阅读 core 层代码、关键逻辑 | 理解笔记 |
| **Recite** | 复述内容 | 向用户确认理解是否正确 | 确认对话 |
| **Review** | 复习巩固 | 沉淀到 experience/issues | 经验文档 |

### 6.3 适用场景

**需求理解阶段**：
``` text
Survey → 浏览需求文档结构
Question → 提出澄清问题
Read → 深入理解需求细节
Recite → 向用户确认理解
Review → 沉淀需求理解笔记
```

**代码理解阶段**：
``` text
Survey → 扫描项目目录结构
Question → 识别核心类和关键方法
Read → 阅读核心代码逻辑
Recite → 向用户确认理解
Review → 沉淀代码理解笔记
```

**经验沉淀阶段**：
``` text
Survey → 浏览 experience/issues 目录
Question → 找到相关的历史经验
Read → 深入阅读经验文档
Recite → 应用到当前任务
Review → 更新或创建新的经验文档
```

### 6.4 方法关系

| 维度 | 说明 |
|------|------|
| **所属层次** | 方法层（具体方法） |
| **上层指导** | 笛卡尔分解原则 → Survey步骤拆分结构；乔哈里窗 → 扩大开放区 |
| **下层应用** | 联动检查（七）：Survey步骤识别关联文件；情境记忆法（十）：Review步骤沉淀 |
| **同层协作** | 苏格拉底提问（四）：Question步骤使用苏格拉底提问 |

## 七、联动检查

### 7.1 核心原则

| 原则 | 说明 |
|------|------|
| **变更即联动** | 任何删除、重命名、移动操作时，必须全局搜索其所有引用 |
| **文档即代码** | 文档中的引用与代码同等重要，变更时必须一并清理 |
| **搜索即验证** | 全局搜索无匹配即为验证通过 |

**触发条件**：
- 删除文件/目录
- 删除枚举/常量/变量
- 重命名类/方法/字段
- 移动文件位置

**全局搜索范围**：
- 代码文件（`.java`）
- 配置文件（`.yml`, `.xml`）
- 资源文件（`.md` prompt）
- 文档（`.md`）
- SQL脚本（`.sql`）

**验证方式**：
- 全局搜索关键词，无匹配即为完成

**强制执行**：
- 删除文件后，立即全局搜索文件名
- 发现引用立即清理
- 无匹配才算完成

### 7.2 执行步骤

| 步骤 | 内容 |
|------|------|
| 1.识别关联 | 分析数据流上下游、共享概念、废弃替代 |
| 2.影响评估 | 高/中/低影响分级 |
| 3.同步修改 | 主动修改关联组件 |
| 4.验证完整 | 检查遗漏 |
| 5.执行后验证 | **执行完成后再次全局搜索，确认无遗留引用** |

**强制执行**：
- 步骤4在执行前完成，步骤5在执行后完成
- 步骤5必须输出验证结果：全局搜索关键词 + 匹配数

### 7.3 检查清单模板

``` text
## 联动检查清单

### 修改点：[节点/文件名称]

| 关联类型 | 关联文件 | 是否需同步 | 修改内容 |
|---------|---------|-----------|---------|
| 数据流上游 | | | |
| 数据流下游 | | | |
| 共享概念 | | | |
| 文档同步 | | | |
```

### 7.4 删除节点场景

删除节点时，必须检查以下关联：

| 关联类型 | 检查项 | 示例 |
|---------|--------|------|
| **数据流上游** | 节点定义、字段注入 | `WorkflowServiceImpl.java` |
| **数据流下游** | 依赖节点、buildPromptContext | `XxxNodeProcessor.java` |
| **数据流下游** | 合并节点依赖 | `SummaryServiceImpl.java` |
| **节点处理器** | 业务实现类 | `XxxNodeProcessor.java` |
| **模板工厂** | TemplateFactory 实现类 | `XxxTemplateFactory.java` |
| **模板目录** | prompt/{domain}/{node}/ 目录 | `prompt/{domain}/{node}/` |
| **枚举定义** | 类型枚举 | `TYPE_*` |
| **注册中心** | Repository 注册 | `registerFactory()` 调用 |
| **变量名** | Java 变量名 vs 模板 {{变量名}} | `dataContent` vs `{{dataContent}}` |

**注意**：
- Entity/Mapper/Service/Controller 可保留（数据库表和历史数据保留）
- **Prompt 变量名必须一致**：Java 代码中的 `putGlobal("xxx")` 必须与 Prompt 模板中的 `{{xxx}}` 对应

## 九、流程执行要点

> **核心原理**：每个步骤都是协作节点，AI 必须输出，人类必须确认，形成闭环

### 9.1 设计原则

| 原则 | 说明 | 防错效果 |
|------|------|---------|
| **每个步骤都是协作节点** | AI 输出 → 人类确认，不是 AI 独自完成 | 避免方向错误 |
| **内部过程不作为独立步骤** | "理解"是内部过程，合并到"确认" | 避免流程冗余 |
| **必须有可见的输出物** | 每步必须有输出，缺少视为流程未完成 | 避免跳过步骤 |
| **顺序正确** | "确认"在"执行"之前，不能跳过 | 避免执行偏差 |

### 9.2 常见错误与预防

| 错误类型 | 表现 | 预防措施 |
|---------|------|---------|
| **跳过确认** | 直接执行，不确认理解 | 强制输出"需求理解复述" |
| **缺少输出** | 步骤执行但无可见输出 | 每步检查输出物 |
| **顺序错误** | 先执行后确认 | 按"确认→规划→执行→自检→沉淀"顺序 |
| **联动遗漏** | 修改代码但未更新关联文件 | 规划阶段输出联动检查清单 |

### 9.3 强制执行保障

| 保障机制 | 说明 |
|---------|------|
| **输出物强制** | 每步必须有输出，缺少视为流程未完成 |
| **顺序强制** | 不可越级执行，必须按顺序 |
| **确认强制** | 未确认不能进入下一步 |

### 9.4 方法关系

| 维度 | 说明 |
|------|------|
| **所属层次** | 执行层（执行保障） |
| **上层指导** | 笛卡尔全面检查 → 每步输出检查表；笛卡尔层次构建 → 确认→规划→执行→自检→沉淀 |
| **下层应用** | 情境记忆法（十）：流程结果沉淀 |
| **同层协作** | 联动检查（七）：规划阶段包含联动检查；沟通进度管理（八）：待办列表跟踪执行 |

## 十、情境记忆法

> **核心原理**：通过将信息与特定情境/场景关联来增强记忆和复用

### 10.1 方法定义

情境记忆法是一种将信息与特定情境绑定的记忆技术，通过"场景触发"实现信息的高效检索和复用。

**AI 协作中的应用**：
- 不是"记住所有"，而是"记住在哪里、什么时候、为什么"
- 通过场景标签快速定位历史经验

### 10.2 适用场景

| 协作阶段 | 应用方式 | 示例 |
|---------|---------|------|
| **需求理解** | 记住业务场景和决策背景 | "这个需求来自XX产品线，背景是..." |
| **代码理解** | 记住代码上下文和设计意图 | "这个类是为了解决XX问题而设计" |
| **经验沉淀** | 记住历史问题的场景和解决方案 | "上次删除节点时遗漏了..." |

### 10.3 实施方法

**沉淀格式**：
``` text
## 场景标签
- 触发条件：什么时候会遇到这个场景？
- 问题类型：这是什么类型的问题？

## 场景描述
描述具体的业务场景和上下文

## 解决方案
描述如何解决这个问题

## 关联经验
链接到相关的经验文档
```

**检索方式**：
``` text
场景触发 → 检索匹配 → 复用方案
```

### 10.4 与 issues/experience 的关系

| 目录 | 作用 | 情境记忆应用 |
|------|------|-------------|
| **issues/** | 记录 AI 犯错的问题 | 触发条件 = 防止再次犯错 |
| **experience/** | 可复用的方法论 | 场景标签 = 方法论适用范围 |

### 10.5 沉淀执行案例

**错误做法**：任务完成后问用户"是否需要沉淀"

**正确做法**：主动判断沉淀类型，输出场景标签，等待确认后执行

**案例**：

``` text
AI输出：
## 沉淀内容

### 场景标签
- 触发条件：修改多章节文档时
- 问题类型：AI协作问题

### 场景描述
修改 collaboration-method.md 时，AI只关注添加新章节，未检查章节顺序是否合理。

### 解决方案
增加"整体结构检查"规范，要求AI修改前输出内容、关系、顺序三方面检查。

### 沉淀路径
- 文件：.iflow/ecosystem/issues/2026-03-02-AI主动性不足.md
- 后续：验证成熟后迁移到 collaboration-method.md

是否允许执行？
```

### 10.6 方法关系

| 维度 | 说明 |
|------|------|
| **所属层次** | 沉淀层（经验固化） |
| **上层指导** | 所有上层方法的输出都可以沉淀：笛卡尔（反思）、乔哈里窗（区域发现）、PDCA（Act阶段）、SQ3R（Review阶段）、联动检查（检查结果）、流程执行（执行结果） |
| **下层应用** | 无（沉淀层是底层） |
| **循环机制** | 沉淀的经验反哺思维层（笛卡尔方法论可从案例学习） |

## 十一、心跳检查方法

> **借鉴自 OpenClaw**: HEARTBEAT 机制，让 AI 主动检查协作状态
> **核心原理**: AI 定期检查协作状态，发现问题，避免遗漏
> **定位**: 执行层（主动机制）

### 11.1 方法定义

心跳检查是一种主动机制，让 AI 定期检查协作状态，发现潜在问题，避免遗漏。

**OpenClaw 的实现**：
- 后台进程每 30 分钟触发
- AI 读取 HEARTBEAT.md 执行检查
- 有问题主动汇报，无事静默

**`.iflow/` 的适配**：
- 纯文档体系无后台进程
- 嵌入到自检阶段，每次任务完成时执行
- 作为"被动流程"中的"主动检查"

### 11.2 核心差异

| 维度 | OpenClaw | `.iflow/` |
|------|---------|----------|
| **触发方式** | 后台进程主动触发 | AI 被调用时嵌入流程 |
| **触发频率** | 每 30 分钟 | 每次任务完成 |
| **执行位置** | 独立的 HEARTBEAT 流程 | 自检阶段的一部分 |
| **核心相同点** | 主动检查、发现问题、避免遗漏 | 主动检查、发现问题、避免遗漏 |

### 11.3 触发条件

| 触发时机 | 检查内容 | 响应方式 |
|---------|---------|---------|
| **每次任务完成后** | 待办、问题、经验 | 输出到自检结果中 |
| **发现问题时** | 是否需要记录到 issues | 主动输出问题记录建议 |
| **上下文过长时** | 是否需要记忆压缩 | 输出压缩建议 |

### 11.4 检查清单

**每次心跳**：
``` text
- [ ] 是否有未完成的待办？
- [ ] issues/ 是否有新问题？
- [ ] 是否有经验需要沉淀？
```

**每日一次（AI 判断是否需要）**：
``` text
- [ ] experience/ 是否需要更新？
- [ ] 规则是否需要补充？
- [ ] 是否需要记忆压缩？
```

### 11.5 响应规范

| 检查结果 | 响应方式 | 示例 |
|---------|---------|------|
| **无事可做** | 静默，不输出 | 输出"无"即可 |
| **有待办** | 主动汇报状态 | "当前有 3 个待办未完成：..." |
| **有问题** | 主动汇报并提出方案 | "发现 issues/ 有新问题，建议..." |
| **有经验** | 输出沉淀内容 | "本次协作有经验可沉淀：..." |

### 11.6 与其他方法的关系

| 维度 | 说明 |
|------|------|
| **所属层次** | 执行层（主动机制） |
| **上层指导** | 笛卡尔全面检查 → 检查待办、问题、经验 |
| **下层应用** | 情境记忆法 → 心跳检查结果沉淀 |
| **同层协作** | 沟通进度管理 → 心跳检查待办状态；联动检查 → 心跳检查关联问题 |

### 11.7 实施要点

1. **静默优先**：无事可做时不输出，避免打扰用户
2. **主动汇报**：有问题或待办时主动汇报，不等待用户询问
3. **精简输出**：心跳检查输出要精简，避免冗长
4. **结合沉淀**：发现经验时使用情境记忆法格式输出

### 11.8 执行示例

**示例1：无事可做**

### 12.1 架构定义

```
┌─────────────────────────────────────────────────────────────┐
│ Layer 0：入口（start.md）                                    │
```

### 12.2 各层职责

| 层级 | 文件类型 | 职责 | 触发方式 |

## 十三、三层保证机制

> **核心原理**：规则自指问题的解决方案——规则写在文件里，谁来保证执行？
> **定位**：框架层，规则执行的保证体系
> **解决问题**：如何让 AI 执行规则？

### 13.1 自指问题

```
规则写在文件里 → AI 读取文件 → AI 理解规则 → AI 执行规则
      ↑                                              │
      └──────────── 如果 AI 不执行呢？←───────────────┘
```

**核心认知**：规则本身无法"自己执行自己"，就像法律无法自己执行自己。

### 13.2 三层机制

| 层级 | 机制 | 作用 | 能否100%保证 |
|------|------|------|-------------|
| **技术层** | system prompt 引用 start.md | 让 AI 强制读取入口文件 | 不能，AI 可能读了不执行 |
| **设计层** | 明确触发条件 + 检查点输出 | 减少模糊性，让 AI 主动声明 | 不能，AI 可能判断不触发 |
| **协作层** | 用户监督 + 反馈 | 用户检查 AI 是否输出了检查点 | 能，人类是最可靠的保证 |

### 13.3 各层具体措施

| 层级 | 措施 | 具体做法 |
|------|------|---------|
| **技术层** | 强制措辞 | 使用"必须"、"强制"，不用"应该"、"建议" |
| **设计层** | 模板填空 | AI 只需填空，不需要自己组织输出 |
| **设计层** | 默认查阅 | 不确定是否触发 → 默认查阅 |
| **协作层** | 用户检查清单 | 用户只需确认"有/无" |

### 13.4 核心洞察

- 技术层 + 设计层：提高 AI 执行率
- 协作层：最终保证（人类是最可靠的）
- 如果不确定是否触发 → **默认查阅**（宁可多查，不可漏查）

## 十六、用户检查清单方法

> **核心原理**：用户只需确认"有/无"，降低认知负担
> **定位**：执行层，协作层的具体实现
> **解决问题**：用户不知道如何验证 AI 是否执行了规范

### 16.1 检查清单设计

| 阶段 | 用户检查项 | 合格标准 |
|------|-----------|---------|

| **确认** | AI 是否输出了"任务边界"？ | 有任务描述 + 有完成条件 |
| **规划** | AI 是否输出了"修改文件列表"？ | 有文件列表 + 有原因 |
| **执行** | AI 是否输出了"修改内容摘要"？ | 有修改摘要 + 有文件路径 |
| **自检** | AI 是否输出了"规则检查表"？ | 有表格 + 有检查结果 |

| "重做xxx" | 不合格，重新执行指定阶段 |

### 16.3 核心价值

- 用户不需要理解复杂的规范

### 18.5 冗余与完整/完成的平衡

**两个平衡**：

| 平衡 | 问题 | 解决方案 |
|------|------|---------|
| **冗余 vs 完整** | 减少重复 vs 确保信息不遗漏 | 核心要点冗余（保证执行），详细内容分离（减少 token） |
| **冗余 vs 完成** | 减少重复 vs 确保任务执行到位 | 检查点输出（保证完成），用户验证（最终保证） |

**平衡原则**：

| 原则 | 说明 |
|------|------|
| 入口有触发 | start.md 有概念/方法论的触发条件 |
| 核心要点冗余 | 每个文件有核心要点，允许与入口重复 |
| 详细内容分离 | 详细内容在具体文件，按需加载 |
| 检查点输出 | 每个阶段必须输出，证明执行了 |
| 用户验证 | 最终由用户验证是否完成 |

### 18.6 步骤组合、排列、打断

**组合**：多个阶段可以组合执行
- 理解 + 获取 → 一次性读取概念和上下文
- 执行 + 沉淀 → 执行完立即沉淀

**排列**：阶段可以重新排列
- 正常：互动 → 理解 → 获取 → 执行 → 沉淀
- 跳过理解：互动 → 获取 → 执行 → 沉淀（已理解的情况）
- 插入理解：执行中遇到问题 → 返回理解 → 继续执行

**打断**：阶段可以被打断
- 用户打断执行 → 记录到 Cache → 下次继续
- AI 遇到阻塞 → 输出问题 → 用户补充 → 继续执行

## 十九、沉淀固化判断标准

> **核心原理**: 沉淀是孵化器，成熟后迁移删除
> **定位**: 沉淀层（经验固化）
> **解决问题**: 如何判断沉淀是否应该固化？固化到哪里？
> **强制执行**: 有沉淀时必须判断是否固化

### 19.1 固化判断原则

**核心问题**：AI是否能在执行时遵守，不重复犯错？

| 判断结果 | 说明 | 处理方式 |
|---------|------|---------|
| AI已遵守 | 规范中有明确触发条件+AI执行了 | 已固化，无需处理 |
| AI犯错过 | 规范中没有触发条件或AI没执行 | 需固化到规范 |
| 未触发 | 本次任务未涉及该场景 | 待观察，暂不处理 |

### 19.2 固化分类原则

| 内容类型 | 固化位置 | 形式 |
|---------|---------|------|
| 贯穿协作全程 | start.md 核心要点 | 精简版 + 详细规范引用 |
| 场景特定触发 | endPoint.md 对应阶段 | 触发条件 + 执行步骤 + 输出模板 + 详细规范引用 |
| 框架/思想类 | collaboration-method.md | 独立章节 |

### 19.3 固化内容原则

| 原则 | 说明 | 示例 |
|------|------|------|
| 要点清晰明了 | 触发条件明确，不模糊 | "精简文档时" vs "需要时" |
| AI易读 | 表格化、模板化、步骤化 | 不用长段落描述 |
| 渐进式映射明确清晰 | 有详细规范引用，触发后可深入 | "详细规范: @xxx.md" |

### 19.4 Cache场景判断原则

**核心区分**：

| 场景 | 用户意图 | Cache操作 | 之后执行 |
|------|---------|----------|---------|
| 用户说"跳过" | 明确不执行 | skipped-tasks.json | ❌ 不执行 |
| 用户说"稍后" | 以后执行 | pending-tasks.json | ✅ 下次执行 |
| 用户没回答 | 未确认 | pending-tasks.json | ✅ 下次确认 |
| 对话结束有未回答 | 挂起 | pending-tasks.json | ✅ 下次预检时提醒 |

**关键洞察**: "跳过" = 不执行；"稍后/没回答" = 待执行

### 19.5 文件审查判断标准

> **核心原则**: 人与AI更好协作，避免AI幻觉和遗忘

**AI记忆特点**：前后记住，中间遗忘

**文件定位判断**：

| 类型 | 定位 | 特点 | 示例 |
|------|------|------|------|
| **入口（start.md）+ 检查（endPoint.md）** | 首尾保证 | 贯穿整个AI，必须一致 | 流程、四层防御、三层保证、强制输出、防止幻觉 |
| **方法/思想/协作方式** | 贯穿 | 入口+检查都要有要点 | 方法论贯穿、协作原则 |
| **规范/原则** | 渐进式披露 | 在规定地方，AI主动获取 | 规则详解、编码规范 |
| **全大写+下划线（*_SPEC.md）** | 目录沉淀 | AI只看当前目录 | IDENTITY_SPEC.md、CACHE_SPEC.md |

**审查一致性判断**：

| 检查项 | 入口（start.md） | 检查（endPoint.md） | 判断 |
|--------|-----------------|---------------------|------|
| 核心要点 | 有 | 有 | 一致 ✅ |
| 核心要点 | 有 | 无 | **需修复** |
| 核心要点 | 无 | 有 | **需修复** |

**错误判断标准**：

| 错误标准 | 正确标准 |
|---------|---------|
| 行数多少 → 判断冗余 | AI是否能在执行时遵守，不重复犯错 |
| 文件分散 → 判断欠缺 | 入口+检查是否一致，渐进式披露是否清晰 |

### 19.6 方法关系

| 维度 | 说明 |
|------|------|
| **所属层次** | 沉淀层（经验固化） |
| **上层指导** | 笛卡尔全面检查 → 判断是否固化完整；乔哈里窗 → 识别盲点区 |
| **下层应用** | 情境记忆法（十）：固化后删除沉淀 |
| **循环机制** | 固化后的规范指导AI执行 → AI执行中发现新问题 → 新沉淀 |

## 二十、Token 经济学方法论

> **核心原理**：分层信息注入实现 Token 效率最大化
> **来源**：Anthropic Skill 系统设计分析
> **定位**：思维层，Token 管理的核心方法
> **解决问题**：如何在有限的 Token 预算下，让 AI 获取足够的上下文？

### 20.1 三层信息模型

| 层级 | 内容 | 加载时机 | Token 消耗 |
|------|------|---------|-----------|
| **L0 概览** | name + description | 启动时加载所有 | ~30 Token/技能 |
| **L1 Body** | SKILL.md 主体 | 激活时加载 | ~500-2000 Token |
| **L2 详细** | references/ 文档 | 按需加载 | ~1000-5000 Token |

### 20.2 在 .iflow 中的应用

| 层级 | .iflow 对应 | 说明 |
|------|------------|------|
| **L0 概览** | start.md 核心要点 | 每次协作强制读取 |
| **L1 Body** | endPoint.md + *_SPEC.md | 触发时按需加载 |
| **L2 详细** | rule/*/skill.md | 深入时按需加载 |

### 20.3 Token 节省效果

```
一次性全部加载：L0 + L1 + L2 ≈ 7000 tokens
渐进加载：L0(~50) → L1(~2000) → L2(~1700) ≈ 3750 tokens
节省：~46%
```

## 二十一、Skill 设计方法论

> **核心原理**：教知识 > 注册 API，效果等价 > 形式等价
> **来源**：Anthropic Skill 系统设计分析
> **定位**：方法层，Skill 设计的核心方法
> **解决问题**：如何设计高效的 Skill？

### 21.1 教知识 > 注册 API

**核心洞察**：LLM 最强的能力是理解自然语言指令后自主解决问题

| 方式 | 思路 | Token 成本 | 灵活性 |
|------|------|-----------|--------|
| **注册 API** | 为每个操作定义 function calling | 高（每个 API ~200-500 Token） | 低（只能调预定义） |
| **教知识** | 通过 SKILL.md 教 LLM 怎么做 | 低（~500-2000 Token 总计） | 高（可创造新操作） |

**设计原则**：
- 优先写好 SKILL.md，而非注册 function calling
- 教 LLM 怎么用工具，而非给 LLM 注册工具
- 让 LLM 有能力创造第 9、10 种操作

### 21.2 效果等价 > 形式等价

**核心原则**：形式不同但效果相同，降低认知负担

| 场景 | 形式等价 | 效果等价 |
|------|---------|---------|
| **沙箱执行** | 脚本必须感知沙箱路径 | 脚本写相对路径，框架处理映射 |
| **符号链接** | 用户必须理解目录结构 | 用户看到正常目录，实际指向隔离区 |
| **降低学习成本** | 必须学习框架特有概念 | 只需了解标准概念 |

**设计原则**：
- 让用户/AI 感知不到复杂性
- 隔离实现细节，暴露简单接口
- 不要求用户/AI 学习框架特有概念

### 21.3 五种 Skill 模式选择

| 模式 | 核心机制 | 适用场景 | 设计要点 |
|------|---------|---------|---------|
| **纯 Prompt 注入** | 仅注入 body | 教规范/风格 | 写好 SKILL.md |
| **脚本执行** | 预制脚本 + skill_run | 操作文件格式 | 脚本 + 使用说明 |
| **库调用** | LLM 写代码 import 库 | 灵活组合 API | 库 + API 文档 |
| **渐进加载** | 路由表 + 按需加载 | 知识量大 | 路由表 + 详细文档 |
| **编排型** | 多阶段工作流 | 复杂流程 | 流水线 + 工具链 |

| 维度 | 说明 |
|------|------|
| **所属层次** | 方法层（具体方法） |
| **上层指导** | Token 经济学（二十）：三层信息模型指导 Skill 文档组织 |
| **应用场景** | skills/ 目录下的所有 Skill 设计 |

## 二十二、执行力公式方法

> **核心原理**：Skill 的执行力 = 文档质量 × 工具能力
> **来源**：Anthropic Skill 系统设计分析
> **定位**：执行层，Skill 质量评估方法
> **解决问题**：如何评估和提升 Skill 的执行力？

### 22.1 执行力公式

```
Skill 的执行力 = SKILL.md body 质量 × (Agent 基础工具 + skill_run 沙箱能力)
```

### 22.2 质量评估维度

| 维度 | 高质量 | 低质量 |
|------|--------|--------|
| **文档质量** | 清晰的使用说明 + 完整的示例 + 触发条件明确 | 只有简单描述 + 无示例 + 触发条件模糊 |
| **工具能力** | 环境隔离 + 增量优化 + 输出收集 | 无隔离 + 无优化 + 输出分散 |

### 22.3 LLM 能力层级

```
开发者（理解 + 组合 + 创造）
    > 选择者（理解 + 选择）
    > 调用者（理解 + 执行）
    > 遵循者（理解 + 遵循）
```

**设计启示**：让 LLM 扮演更高层级的角色，需要更好的文档质量。

### 22.4 质量提升方法

| 问题 | 提升方法 |
|------|---------|
| 文档质量不足 | 补充使用说明、添加示例、明确触发条件 |
| 工具能力不足 | 增强沙箱、添加增量优化、收集输出 |

### 22.5 方法关系

| 维度 | 说明 |
|------|------|
| **所属层次** | 执行层（执行保障） |
| **上层指导** | Skill 设计方法论（二十一）：执行力公式评估 Skill 设计效果 |
| **应用场景** | Skill 质量评估、持续改进 |
