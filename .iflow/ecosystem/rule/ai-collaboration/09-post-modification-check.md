# 修改后自检

## 规则 9：修改后自检

**规则内容**：修改代码后必须自检，也就是此规则 → 检查所有修改和新创建的文件，对照 rule.md 验证，消除 IDE 警告；思想：修改代码后进行完整性检查，避免遗漏问题

## 为什么需要修改后自检

修改代码后进行完整性检查，避免遗漏问题，消除 IDE 警告，确保代码质量。

## 常见错误案例

### 错误1：修改后未检查
**错误做法**：修改代码后直接提交，未进行自检

**问题**：遗漏了 IDE 警告，导致代码质量问题。

### 错误2：检查不完整
**错误做法**：只检查了编译错误，未检查 IDE 警告

**问题**：IDE 警告可能隐藏潜在问题。

### 错误3：未对照 rule.md 验证
**错误做法**：只检查了编译和 IDE 警告，未对照 rule.md 验证

**问题**：可能违反了项目规则。

## 如何检查

### 检查清单

修改完成后必须检查以下内容：

#### 1. 代码规范
- [ ] 是否使用了 @Autowired 注入？（应该使用 @RequiredArgsConstructor + final 字段）
- [ ] 是否使用了内部类？（应该使用顶级类）
- [ ] 是否使用了路径类的指定引用？（应该使用 import 导入类）
- [ ] 是否使用了废弃的类？（应该进行替换引用）
- [ ] 是否使用了硬编码？（应该使用枚举或常量类）
- [ ] 是否使用了 Lombok 依赖？（应该使用 @Data, @RequiredArgsConstructor, @Builder 等）
- [ ] 是否按照 javadoc 规范写好注释？（应该包括创建原因、使用场景、设计思想、对应边界）
- [ ] 数据库操作是否实现幂等性？（应该根据主键是否存在自动选择 insert 或 update）

#### 2. 设计原则
- [ ] 是否删除了接口方法后同步删除实现类中的方法、相关依赖注入字段和 import 语句？
- [ ] 是否避免了过度设计？（应该禁止使用 demo 和 TODO）
- [ ] 是否使用了已经存在的变量？（应该减少变量数量，降低认知负担）
- [ ] 是否保持了方法签名一致？（应该确保方法参数一致，修改方法时同步更新所有调用点）
- [ ] 是否保持了修改完整性？（应该检查步骤是否完整、注释编号是否连续、变量名是否一致、逻辑是否正确）
- [ ] 是否创建了未使用的代码？（应该不创建未使用的代码）

#### 3. 配置管理
- [ ] 是否通过配置类统一管理外部服务的 URL 和路径？（应该不允许在服务实现中硬编码）

#### 4. 代码风格
- [ ] 是否有悬空的 Javadoc？（应该每个 Javadoc 必须紧跟方法/类）
- [ ] 是否有重复的 Javadoc？（应该同一个方法只能有一个 Javadoc 块）
- [ ] 是否有多余的空白行？（应该方法之间只保留一个空行）

#### 5. 语言特性
- [ ] 是否使用了 JDK 17 新特性？（应该使用 Record、instanceof 模式匹配、switch 表达式、var、文本块）
- [ ] 是否正确使用了 var？（应该仅限类型显而易见的情况，泛型类型使用显式类型声明）

#### 6. 文档规范
- [ ] 是否按照 Markdown 格式编写文档？（代码块必须使用三个反引号加空格加语言标识符的格式）
- [ ] 是否未经允许创建了 md 格式的总结之类的文档？（应该避免文档泛滥）

#### 7. 交互规范
- [ ] 是否阐明了步骤？（应该直奔重点但别忽略细节）
- [ ] 是否先说明了对需求的理解？（应该经过双方讨论之后同意开展工作）

#### 8. 质量规范
- [ ] 是否确保了并发安全？（应该优先使用局部变量而非实例变量，避免使用单例模式管理可变状态）
- [ ] 是否遵循了渐进式优化？（应该先实现基本功能，再逐步完善）

#### 9. 接口参数校验规范
- [ ] 外部接口参数转换是否在 DTO 层处理？（应该 DTO 提供规范化方法，Service 层使用规范化方法）

#### 10. 命名语义规范
- [ ] 是否避免了命名混淆？（应该使用成对命名，区分常量命名和变量命名）

#### 11. 全面分析规范
- [ ] 是否使用了多维度分析框架？（应该从功能、性能、可读性、可维护性、命名等维度全面分析）

### 检查步骤

#### 步骤1：编译检查（必须）
运行 `mvn compile` 确保无编译错误。

#### 步骤2：IDE 警告检查（必须）
消除所有 IDE 警告。

#### 步骤3：对照 rule.md 验证（必须）
对照 rule.md 验证所有修改，确保遵循所有规则。

#### 步骤4：检查新创建的文件（必须）
检查所有新创建的文件，确保符合规范。

#### 步骤5：检查修改的文件（必须）
检查所有修改的文件，确保符合规范。

## 常见误区

1. **以为编译通过就没问题**：还需要消除 IDE 警告
2. **以为 IDE 警告可以忽略**：IDE 警告可能隐藏潜在问题
3. **以为不需要对照 rule.md 验证**：必须对照 rule.md 验证，确保遵循所有规则
4. **以为可以跳过新创建的文件**：必须检查所有新创建的文件

## 最佳实践

### 实践1：完整的自检流程
修改代码后必须进行完整的自检流程，包括编译检查、IDE 警告检查、对照 rule.md 验证、检查新创建的文件、检查修改的文件。

### 实践2：消除所有 IDE 警告
必须消除所有 IDE 警告，不能忽略任何警告。

### 实践3：对照 rule.md 验证
必须对照 rule.md 验证所有修改，确保遵循所有规则。

### 实践4：检查所有文件
必须检查所有新创建的文件和修改的文件，确保符合规范。

## 执行原则

- 每个步骤必须完成才能进行下一步
- 如果发现错误，必须修复后才能继续
- 所有步骤完成后才能回复用户
