## 一、背景与目标

### 1.1 背景

电商系统需要一套完整的支付解决方案，支持多种支付渠道，确保支付过程安全、可靠、可追溯。本 demo 用于指导新人理解支付系统的核心设计和实现要点。

### 1.2 目标

**核心目标**:
1. 支持微信、支付宝双渠道支付
2. 实现支付对账功能，确保资金安全
3. 支持高并发支付场景，保证系统稳定性
4. 支持完整的退款流程

**成功指标**:
- 支付成功率：>99.9%
- 支付响应时间：<3秒
- 对账准确率：100%
- 并发支持：>1000 QPS

## 四、详细需求

### 4.1 多渠道支付

#### 4.1.1 微信支付

**输入**:
- 订单号: String，必填，唯一标识
- 订单金额: BigDecimal，必填，单位：元
- 商品描述: String，必填，最长127字符
- 用户openid: String，小程序支付必填

**处理逻辑**:
1. 校验订单状态（待支付）
2. 调用微信统一下单接口
3. 生成预支付交易会话标识
4. 返回支付参数给前端

**输出**:
- 预支付ID: prepay_id
- 支付签名: paySign
- 签名类型: signType

**异常处理**:
- 余额不足: 提示用户更换支付方式
- 网络超时: 订单保持待支付状态，支持重试
- 重复支付: 幂等处理，返回原支付结果

#### 4.1.2 支付宝支付

**输入**:
- 订单号: String，必填，唯一标识
- 订单金额: BigDecimal，必填，单位：元
- 商品标题: String，必填
- 商品描述: String，可选

**处理逻辑**:
1. 校验订单状态（待支付）
2. 调用支付宝统一下单接口
3. 生成支付表单或二维码
4. 返回支付参数给前端

**输出**:
- 支付表单: form表单（PC网页支付）
- 支付链接: qr_pay_mode（扫码支付）

**异常处理**:
- 余额不足: 提示用户更换支付方式
- 网络超时: 订单保持待支付状态，支持重试
- 重复支付: 幂等处理，返回原支付结果

---

### 4.2 支付回调

#### 输入
- 支付渠道: 枚举（WECHAT/ALIPAY）
- 回调数据: JSON/XML，第三方加密数据

#### 处理逻辑

``` text
1. 验证签名（防止伪造回调）
   - 使用第三方公钥验签
   - 验证时间戳防止重放攻击

2. 解析回调数据
   - 提取订单号、支付金额、交易流水号

3. 幂等校验
   - 检查订单是否已支付
   - 已支付则直接返回成功

4. 更新订单状态
   - 订单状态：待支付 → 已支付
   - 记录支付流水号
   - 记录支付时间

5. 返回成功响应
   - 告知第三方已处理成功
```

#### 输出
- 成功响应: "SUCCESS"（微信）或 "success"（支付宝）
- 失败响应: "FAIL"

#### 异常处理
- 签名验证失败: 记录日志，返回失败
- 订单不存在: 记录异常日志，返回失败
- 金额不一致: 记录异常，触发人工审核

---

### 4.3 支付对账

#### 输入
- 对账日期: Date，默认前一天
- 支付渠道: 枚举（WECHAT/ALIPAY/ALL）

#### 处理逻辑

``` text
1. 下载第三方账单
   - 微信：downloadbill接口
   - 支付宝：alipay.data.dataservice.bill.downloadurl.query

2. 解析账单数据
   - 提取交易时间、订单号、金额、交易状态

3. 与本地订单比对
   - 遍历本地已支付订单
   - 匹配第三方账单记录

4. 记录差异
   - 本地有，第三方无：可疑支付，需核实
   - 第三方有，本地无：漏单，需补录

5. 生成对账报告
   - 成功笔数、成功金额
   - 差异笔数、差异金额
   - 差异明细
```

#### 输出
- 对账报告:
  - 总交易笔数
  - 总交易金额
  - 差异笔数
  - 差异明细列表

#### 异常处理
- 账单下载失败: 重试3次，记录告警
- 账单解析失败: 记录异常，人工介入
- 大额差异: 触发告警，人工审核

---

### 4.4 并发支付

#### 场景描述
高并发场景下（如秒杀活动），需要保证：
1. 同一订单不会被重复支付
2. 库存不会被超卖
3. 支付请求不会丢失

#### 设计方案

**1. 幂等性设计**
``` text
幂等Key = 订单号 + 支付渠道 + 时间戳（分钟级）
Redis SETNX 实现幂等锁，有效期5分钟
```

**2. 分布式锁**
``` text
锁Key = ORDER_PAY_LOCK:订单号
Redis Redlock 实现分布式锁
锁过期时间：30秒
```

**3. 异步处理**
``` text
支付请求 → 消息队列 → 支付处理器 → 更新订单
```

**4. 库存扣减**
``` text
支付成功 → 扣减库存（乐观锁）→ 发货
库存不足 → 自动退款
```

#### 并发控制要点

| 场景 | 控制方式 | 说明 |
|------|---------|------|
| 重复支付 | 幂等Key + 分布式锁 | 同一订单同时只能有一个支付请求处理 |
| 超卖 | 乐观锁 + 库存预扣 | 下单时预扣库存，支付失败回滚 |
| 请求丢失 | 消息队列持久化 | 支付请求写入MQ，保证不丢失 |
| 数据一致 | 本地消息表 + 定时补偿 | 支付状态与订单状态最终一致 |

### 4.5 退款功能

#### 输入
- 订单号: String，必填
- 退款金额: BigDecimal，必填，≤订单金额
- 退款原因: String，必填
- 操作人: String，必填

#### 处理逻辑

``` text
1. 校验订单状态
   - 订单必须是已支付状态
   - 退款金额≤已支付金额-已退款金额

2. 创建退款记录
   - 退款单号（唯一）
   - 退款金额、退款原因
   - 退款状态：待审核

3. 退款审核（可选）
   - 小额退款自动通过
   - 大额退款需人工审核

4. 调用第三方退款接口
   - 微信：/v3/refund/domestic/refunds
   - 支付宝：alipay.trade.refund

5. 更新退款状态
   - 退款状态：待审核 → 已退款
   - 记录退款流水号

6. 回滚库存（如需要）
```

#### 输出
- 退款单号: String
- 退款状态: 枚举（待审核/已退款/退款失败）
- 退款时间: DateTime

#### 异常处理
- 退款超时: 重试3次，记录异常
- 退款失败: 记录失败原因，人工处理
- 部分退款: 支持多次部分退款，累计不超过订单金额
