# OpenClaw 集成方案

> **定位**: OpenClaw核心思想与当前项目的集成方案
> **核心要点（必须记住）**
> - **当前项目定位**：文档工程（规范传递），不是运行时框架（多Agent协作）
> - **适用原则**：借鉴设计思想，不是照搬文件结构
> - OpenClaw 核心思想：Workspace-First、分层身份、四层记忆、Skills延迟加载
> - 心跳在纯文档体系无法主动触发，需在整个任务周期中保持AI主动性
> - 把方法论嵌入流程，而不是独立文档
> - `.iflow/` 目录是通用的（可分享），`app-demand/` 是项目专用的
> - **Loop 模式**：AI 不执行任何实质性操作，除非获得人类确认
> - **Cache 机制**：贯穿整个 AI 执行生命周期，不是独立功能

### 核心原则

**在任务未完成前，AI不退出，保持主动性。**

### 主动检查点

| 阶段 | AI主动行为 | 触发条件 |

## 六、Loop 模式与 Cache 机制

### 核心问题

**AI 能否"主动"执行？**

| 问题 | 答案 | 原因 |
|------|------|------|
| AI 能主动启动 Python 吗？ | **不能真正"主动"** | AI 只在被调用时执行命令 |
| Cache 能保证一直执行吗？ | **不能** | AI 只在用户对话时存在，cache 只能保证"下次被调用时继续" |

**根本限制**：AI 没有"持续存在"的能力，每次对话都是独立的。

### Loop 模式

**核心原则**：AI 不执行任何实质性操作，除非获得人类确认。

``` text
┌─────────────────────────────────────┐
│           LOOP 模式                 │
├─────────────────────────────────────┤
│ AI 输出方案 + "是否执行？[Y/n/跳过]" │
│                                      │
│ 用户回答：                           │
│ - Y/执行 → AI 执行 → 更新进度        │
│ - n/不执行 → AI 修改方案              │
│ - 跳过 → AI 记录到 cache，继续下一个   │
│ - 讨论 → AI 进入细节讨论              │
│                                      │
│ AI 执行完成 → 输出进度 + 继续询问     │
└─────────────────────────────────────┘
```

### Cache 机制

**详细规范**: `@.iflow/cache/CACHE_SPEC.md `

**目录结构**：

``` text
.iflow/cache/
├── CACHE_SPEC.md        # Cache 规范
├── pending-tasks.json   # 待确认任务
├── skipped-tasks.json   # 跳过的任务
└── task-progress.json   # 任务进度
```

**首次问候检查**：每次对话开始时，AI 检查 cache 目录，如有待办则输出提醒。

### 关键洞察

1. **诚实承认局限**：AI 不能真正"主动"，只能"被动触发"
2. **Loop 模式**：每个动作都要确认，避免 AI 自作主张
3. **Cache 机制**：保证任务跨对话连续性
4. **任务边界输出**：每次输出"任务边界 + 完成条件 + 当前进度"

## 七、经验沉淀

### 沉淀 1: 角色定位修正

**场景标签**: `#角色定义` `#协作传递` `#身份体系`

**场景描述**: 
在 AI 协作文档工程中，AI 的角色不是"教师"，而是"协作规范传递者"。AI 教师暗示存在"学生"，但实际上是将经验传递给其他 AI 实例。

**解决方案**:
- 角色：`AI 协作助手 + 协作规范传递者`
- 传递对象：其他 AI 实例（非"AI 学生"）
- 传递内容：协作规范、经验沉淀
- 文件修改：identity.md、soul.md

---

### 沉淀 2: 四层防御体系

**场景标签**: `#冷启动` `#Cache` `#状态管理` `#防御体系`

**场景描述**: 
原有的三层防御体系缺少状态层。Cache 机制应作为 Level 0（状态层），与冷启动的 Level 1-3（初始化层）形成完整的四层防御体系。

**解决方案**:
``` text
Level 0: 状态层（Cache） → 解决"我做到哪里了？"
Level 1: 项目级冷启动 → 解决"项目规范是什么？"
Level 2: 需求级冷启动 → 解决"需求背景是什么？"
Level 3: 任务级执行清单 → 解决"具体怎么执行？"
```
- 关键关系：Cache 是状态层（当前进度），冷启动是初始化层（背景上下文）
- 文件修改：cold-start.md、CACHE_SPEC.md、endPoint.md

---

### 沉淀 3: 自指检查

**场景标签**: `#自检` `#自指` `#执行验证`

**场景描述**: 
当 AI 提出新的方法或规范时，必须验证自己是否执行了该方法。例如，提出"四层防御体系"后，必须检查自己是否已将 Cache 集成到防御体系中。

**解决方案**:
在自检环节增加"自指检查"：
``` markdown
### 自指检查
**我是否执行了我正在提出的方法？**
| 提出的方法 | 是否执行 | 说明 |
|-----------|---------|------|
| 四层防御体系 | ✅ 是 | 已修改 cold-start.md |
```

### 沉淀 5: AI幻觉检查

**场景标签**: `#AI幻觉` `#自检` `#自指检查` `#修改.iflow`

**场景描述**: 
当用户说"依照 @.iflow/start.md 执行"时，AI 可能"以为"自己执行了所有检查，但实际只是输出一句话"已完成预检"而没有具体证据。这就是 AI 幻觉——AI 对自己行为的虚假认知。

**幻觉类型**：

| 幻觉类型 | 表现 | 危害 |
|---------|------|------|
| 执行幻觉 | 输出"已执行"但没有具体证据 | 遗漏关键步骤 |
| 读取幻觉 | 输出"已读取"但没有内容摘要 | 没有真正理解内容 |
| 检查幻觉 | 输出"已检查"但没有检查结果表格 | 检查流于形式 |
| 自指幻觉 | 提出新方法但没有验证自己是否执行 | 新方法形同虚设 |

**检测方法：强制输出模板**

**问题**：怎么让AI真的执行？

**解决方案**：
1. **强制填空**：每个阶段有固定模板，AI 必须填满才能进入下一阶段
2. **证据要求**：自指检查需要"证据"，不是简单的 ✅/❌
3. **表格约束**：检查结果必须用表格输出，不能一句话带过

**例子（抽象场景）**：

``` text
场景：用户说"修改 endPoint.md 增加新的检查机制，依照 start.md 执行"

❌ AI幻觉输出：
## 预检
已完成四层防御检查，身份确认，概念无阻塞。

✅ 正确输出：
## 预检

### 1. 四层防御检查
| Level | 名称 | 检查结果 | 是否读取 |
|-------|------|---------|---------|
| 0 | Cache 状态层 | 无待办任务 | ✅ |
| 1 | 项目级冷启动 | 非新项目 | ❌ |
| 2 | 需求级冷启动 | 非新需求 | ❌ |
| 3 | 任务级执行清单 | 需要 | ✅ |

### 2. 身份确认
- 已读取：identity.md / soul.md / user.md
...
```

**适用范围**：
- ✅ 修改 .iflow 文件（AI协作相关）时必须
- ❌ 修改代码文件时不需要（代码有编译验证）

**关键洞察**：AI 幻觉无法完全消除，但可以通过"强制输出模板"让幻觉暴露出来——如果 AI 填不满表格，就说明没有真正执行。

### 沉淀 6: start.md 与 endPoint.md 的分工

**场景标签**: `#入口设计` `#冗余平衡` `#记忆规律`

**场景描述**: 
start.md 和 endPoint.md 存在内容重复。根据 AI 记忆规律"前后记住，中间遗忘"，两者都需要强调关键检查点，但不能简单重复。

**分工原则**：

| 文件 | 定位 | 内容 |
|------|------|------|
| **start.md** | 入口索引 | "要做什么" + 强制输出模板（精简版） |
| **endPoint.md** | 执行手册 | "怎么做" + 详细规范 |

**平衡强调与冗余**：

| 正确的强调 | 错误的冗余 |
|-----------|-----------|
| 首尾重复"关键检查点" | 首尾重复"详细流程描述" |
| start 简洁 + end 详细 | start 和 end 内容相同 |

**关键洞察**: 强调 ≠ 重复全部内容。强制输出模板放在 start.md（入口，容易记住），详细规范放在 endPoint.md（兜底，详细说明）。

### 沉淀 7: 交互友好性

**场景标签**: `#交互设计` `#确认机制`

**场景描述**: 
频繁询问"是否进入下一阶段"不是友好的交互。AI 应该只在需要用户补充数据时才询问。

**改进原则**：

| 场景 | AI行为 |
|------|--------|
| 有需要用户补充的数据 | 询问，列出需要补充的内容 |
| 没有问题需要补充 | 默认执行下一阶段，不询问 |
| 关键操作（git commit等） | 必须确认 |

**关键洞察**: 减少不必要的确认，只在真正需要人类输入时才打断流程。

### 沉淀 8: 删除前评估机制

**场景标签**: `#删除评估` `#保护机制` `#防止错误`

**场景描述**: 
AI 在精简或修改文档时，可能删除重要内容而没有意识到。例如：精简 start.md 时删除了"人格定义"和"加载策略"，这些是 AI 需要知道"我是谁"和"怎么加载"的关键内容。

**问题根源**：
- 只关注"精简"目标，没评估每个内容的重要性
- 没有删除前评估机制
- 没有标记"不能删除"的内容

**解决方案**：

**删除前评估流程**：

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 列出要删除的内容 | 明确删除范围 |
| 2 | 评估每个内容的重要性 | 高/中/低 |
| 3 | 高重要性 → 必须保留或迁移 | 不能删除 |
| 4 | 中重要性 → 精简但保留要点 | 可精简 |
| 5 | 低重要性 → 可以删除 | 可删除 |

**删除前评估模板**：

``` text
### 删除前评估

| 内容 | 重要性 | 处理方式 | 原因 |
|------|--------|---------|------|
| 内容1 | 高/中/低 | 保留/迁移/删除 | ... |
```

**关键洞察**: 任何"精简"操作都必须先评估，不能直接删除。高重要性的内容（如人格定义、加载策略）必须保留。

---

### 沉淀 9: 触发条件与证据原则

**场景标签**: `#触发条件` `#证据原则` `#强制执行`

**场景描述**: 
强制输出模板不能总是执行（代码修改有编译验证），也不能从不执行（AI协作修改无验证）。需要明确的触发条件和证据原则。

**触发条件**：

| 场景 | 是否使用模板 | 原因 |
|------|-------------|------|
| 修改 .iflow 文件 | ✅ 必须 | 涉及 AI 协作规范，无编译验证 |
| 修改代码文件 | ❌ 不必须 | 有编译验证 |
| 单次简单问答 | ❌ 不必须 | 无需跨对话 |
| 跨对话任务 | ✅ 必须 | 需要 Cache 支持 |

**证据原则**：
- ❌ 错误："已完成预检"
- ✅ 正确："已读取 task-progress.json，current_task = task-001，进度 2/4"

**关键洞察**: 触发条件让 AI 知道"何时必须执行"，证据原则让 AI 知道"如何证明执行了"。

### 沉淀 10: Cache 全生命周期触发

**场景标签**: `#Cache` `#全生命周期` `#防止遗漏`

**场景描述**: 
Cache 不能只在某个阶段读写，必须贯穿整个生命周期，否则会出现"以为执行了，实际没有"的幻觉。

**全生命周期触发**：

| 阶段 | Cache 操作 | 验证方式 |
|------|-----------|---------|
| 预检 | 读取 Cache | 输出具体内容，不是"有/无" |
| 确认 | 写入任务边界 | 更新 task-progress.json |
| 执行 | 更新进度 | 更新 completion_conditions |
| 自检 | 验证 Cache | 读取并输出具体状态 |
| 沉淀 | 清理 Cache | 移动到 completed_tasks |

**关键洞察**: Cache 是 AI 记忆的延伸，必须在整个生命周期中持续读写，否则 AI 会"忘记"自己做了什么。

### 沉淀 11: 关键操作确认的边界理解

**场景标签**: `#关键操作` `#确认机制` `#误解风险`

**场景描述**: 
用户回复"git message"，AI 理解为"确认提交"并执行了 git commit。但实际上用户是想"看 commit message"，不是"确认提交"。

**问题根源**：
- 用户回复含糊，AI 主动解读
- AI 急于执行，没有二次确认
- 关键操作的确认边界不清晰

**解决方案**：

**确认边界判断表**：

| 用户回复 | 正确理解 | AI 行为 |
|---------|---------|--------|
| "Y/是/确认/执行" | 明确同意 | 执行 |
| "git message" | 想看消息 | 输出消息，等待确认 |
| "看看效果" | 想预览 | 输出预览，等待确认 |
| 沉默/无回复 | 未确认 | 不执行，再次询问 |
| "跳过" | 不执行本次 | 记录到 Cache，继续 |

**关键洞察**: 
- 关键操作的确认必须是**明确同意**，不能是**推断同意**
- 不确定时，宁可多问一次，也不要擅自执行
- "形式上问了"不等于"真正确认了"
