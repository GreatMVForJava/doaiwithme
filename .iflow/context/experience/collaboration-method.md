# 协作方法

> **适用场景**: AI与人类协作过程中的提问策略、联动检查、沟通模式
> **核心目的**: 扩大开放区、避免AI犯错、提高协作效率

---

## 一、乔哈里窗协作模式

### 1.1 四区域定义

| 区域 | 定义 | AI协作场景 |
|------|------|-----------|
| **开放区** | 双方都知道 | rule.md、需求文档中明确记录的内容 |
| **盲点区** | 人类知道，AI不知道 | 业务背景、隐含需求、行业约束 |
| **隐藏区** | AI知道，人类没表达 | 技术细节、实现方案、潜在风险 |
| **未知区** | 双方都不知道 | 执行中才暴露的问题、边界情况 |

### 1.2 协作目标

**核心目标**：扩大开放区，缩小盲点区和隐藏区，探索未知区

---

## 二、提问策略（苏格拉底五步骤）

### 2.1 五步骤

| 步骤 | 名称 | 核心问题 | 适用区域 |
|------|------|---------|---------|
| 1 | 本体与定义 | "这究竟是什么？" | 盲点区 |
| 2 | 机制与因果 | "结果背后的动力系统是什么？" | 隐藏区 |
| 3 | 边界与约束 | "如果失败，最可能死在哪？" | 隐藏区 |
| 4 | 框架与视角 | "跨学科如何合成？" | 未知区 |
| 5 | 合成与应用 | "综合输出最终方案" | 开放区 |

### 2.2 工具选择

| 区域 | 首选工具 | 方法 |
|------|---------|------|
| 开放区 | rule3直接执行 | 无需提问 |
| 盲点区 | AskUserQuestionTool | 结构化确认 |
| 隐藏区 | 苏格拉底提示法 | 引导澄清 |
| 未知区 | 苏格拉底+PDCA | 探索+验证 |

### 2.3 提问示例

**本体与定义**：
``` text
普通："帮我优化这个Prompt"
苏格拉底："这个Prompt的本质目的是什么？用户真正想要什么？"
```

**边界与约束**：
``` text
普通："执行这个方案"
苏格拉底："如果方案失败，最可能是什么原因？"
```

## 三、联动检查

### 3.1 核心原则

| 原则 | 说明 |
|------|------|
| **变更即联动** | 任何删除、重命名、移动操作时，必须全局搜索其所有引用 |
| **文档即代码** | 文档中的引用与代码同等重要，变更时必须一并清理 |
| **搜索即验证** | 全局搜索无匹配即为验证通过 |

**触发条件**：
- 删除文件/目录
- 删除枚举/常量/变量
- 重命名类/方法/字段
- 移动文件位置

**全局搜索范围**：
- 代码文件（`.java`）
- 配置文件（`.yml`, `.xml`）
- 资源文件（`.md` prompt）
- 文档（`.md`）
- SQL脚本（`.sql`）

**验证方式**：
- 全局搜索关键词，无匹配即为完成

**强制执行**：
- 删除文件后，立即全局搜索文件名
- 发现引用立即清理
- 无匹配才算完成

### 3.2 执行步骤

| 步骤 | 内容 |
|------|------|
| 1.识别关联 | 分析数据流上下游、共享概念、废弃替代 |
| 2.影响评估 | 高/中/低影响分级 |
| 3.同步修改 | 主动修改关联组件 |
| 4.验证完整 | 检查遗漏 |
| 5.执行后验证 | **执行完成后再次全局搜索，确认无遗留引用** |

**强制执行**：
- 步骤4在执行前完成，步骤5在执行后完成
- 步骤5必须输出验证结果：全局搜索关键词 + 匹配数

### 3.3 检查清单模板

``` text
## 联动检查清单

### 修改点：[节点/文件名称]

| 关联类型 | 关联文件 | 是否需同步 | 修改内容 |
|---------|---------|-----------|---------|
| 数据流上游 | | | |
| 数据流下游 | | | |
| 共享概念 | | | |
| 文档同步 | | | |
```

### 3.4 删除节点场景

删除节点时，必须检查以下关联：

| 关联类型 | 检查项 | 示例 |
|---------|--------|------|
| **数据流上游** | 节点定义、字段注入 | `WorkflowServiceImpl.java` |
| **数据流下游** | 依赖节点、buildPromptContext | `XxxNodeProcessor.java` |
| **数据流下游** | 合并节点依赖 | `SummaryServiceImpl.java` |
| **节点处理器** | 业务实现类 | `XxxNodeProcessor.java` |
| **模板工厂** | TemplateFactory 实现类 | `XxxTemplateFactory.java` |
| **模板目录** | prompt/{domain}/{node}/ 目录 | `prompt/{domain}/{node}/` |
| **枚举定义** | 类型枚举 | `TYPE_*` |
| **注册中心** | Repository 注册 | `registerFactory()` 调用 |
| **变量名** | Java 变量名 vs 模板 {{变量名}} | `dataContent` vs `{{dataContent}}` |

**注意**：
- Entity/Mapper/Service/Controller 可保留（数据库表和历史数据保留）
- **Prompt 变量名必须一致**：Java 代码中的 `putGlobal("xxx")` 必须与 Prompt 模板中的 `{{xxx}}` 对应

## 四、区域转化方法

### 4.1 盲点区→开放区

- 用户主动分享背景信息
- AI使用AskUserQuestionTool确认

### 4.2 隐藏区→开放区

- AI主动暴露技术假设
- 使用苏格拉底提示法引导

### 4.3 未知区→开放区

- 使用PDCA迭代探索
- 小范围试错，快速验证

## 五、未知区处理方案

### 5.1 方法融合

``` text
框架与视角 → 假设驱动 → PDCA验证
```

### 5.2 PDCA循环

| 阶段 | 内容 | 输出物 |
|------|------|--------|
| Plan | 提出假设/方案 | 假设陈述、方案大纲 |
| Do | 小范围执行 | 执行记录、中间结果 |
| Check | 检查结果 | 验证报告、问题清单 |
| Act | 调整改进 | 改进方案、经验沉淀 |

### 5.3 强制执行

**触发条件**：遇到未知区问题时，必须使用 PDCA 循环

**执行流程**：
1. **Plan**：明确假设，输出假设陈述
2. **Do**：小范围试错，输出执行记录
3. **Check**：验证假设，输出验证报告
4. **Act**：根据结果调整，输出改进方案

**输出物强制**：
- 每个阶段必须有输出物
- 缺少输出物视为流程未完成
- 完成后使用场景标签格式沉淀经验

## 六、沟通进度管理

### 6.1 核心原则

**沟通即任务**：每次沟通点都应记录在待办列表中，避免遗漏

### 6.2 执行方式

| 阶段 | 操作 | 状态标记 |
|------|------|---------|
| 用户提出问题/需求 | 添加到待办列表 | pending |
| AI确认理解 | 回复确认 | completed |
| AI执行任务 | 开始执行 | in_progress |
| 任务完成 | 更新状态 | completed |

### 6.3 效果

- **避免遗漏**：每个讨论点都有记录
- **进度可视**：用户清晰看到当前状态
- **协作闭环**：沟通→确认→执行→完成，全程可追溯
- **降低认知负担**：列表替AI记，不依赖记忆

### 6.4 示例

``` text
用户：rule.md 有什么可以修改的

AI待办列表：
☐ 读取 experience/ 和 issues/ 目录
☐ 确认用户对修改的期望范围
☐ 分析 rule.md 问题
☐ 提出修改方案
☐ 等待用户确认
☐ 执行修改
☐ 执行修改后自检
☐ 沉淀本次协作经验
```

## 七、情境记忆法

> **核心原理**：通过将信息与特定情境/场景关联来增强记忆和复用

### 7.1 方法定义

情境记忆法是一种将信息与特定情境绑定的记忆技术，通过"场景触发"实现信息的高效检索和复用。

**AI 协作中的应用**：
- 不是"记住所有"，而是"记住在哪里、什么时候、为什么"
- 通过场景标签快速定位历史经验

### 7.2 适用场景

| 协作阶段 | 应用方式 | 示例 |
|---------|---------|------|
| **需求理解** | 记住业务场景和决策背景 | "这个需求来自XX产品线，背景是..." |
| **代码理解** | 记住代码上下文和设计意图 | "这个类是为了解决XX问题而设计" |
| **经验沉淀** | 记住历史问题的场景和解决方案 | "上次删除节点时遗漏了..." |

### 7.3 实施方法

**沉淀格式**：
``` text
## 场景标签
- 触发条件：什么时候会遇到这个场景？
- 问题类型：这是什么类型的问题？

## 场景描述
描述具体的业务场景和上下文

## 解决方案
描述如何解决这个问题

## 关联经验
链接到相关的经验文档
```

**检索方式**：
``` text
场景触发 → 检索匹配 → 复用方案
```

### 7.4 与 issues/experience 的关系

| 目录 | 作用 | 情境记忆应用 |
|------|------|-------------|
| **issues/** | 记录 AI 犯错的问题 | 触发条件 = 防止再次犯错 |
| **experience/** | 可复用的方法论 | 场景标签 = 方法论适用范围 |

## 八、SQ3R 阅读法

> **核心原理**：系统化阅读，从浏览到内化的完整流程

### 8.1 方法定义

SQ3R 是一种系统化的阅读理解方法，包含五个步骤：
- **S**urvey（浏览）：快速浏览整体结构
- **Q**uestion（提问）：提出关键问题
- **R**ead（阅读）：深入阅读关键内容
- **R**ecite（复述）：用自己的话复述
- **R**eview（复习）：回顾和巩固

### 8.2 AI 协作适配

| 步骤 | 原始含义 | AI 协作适配 | 输出 |
|------|---------|------------|------|
| **Survey** | 浏览目录和结构 | 快速扫描文件目录、import 关系 | 整体结构图 |
| **Question** | 提出阅读问题 | 识别核心类、关键方法、数据流向 | 问题列表 |
| **Read** | 深入阅读 | 阅读 core 层代码、关键逻辑 | 理解笔记 |
| **Recite** | 复述内容 | 向用户确认理解是否正确 | 确认对话 |
| **Review** | 复习巩固 | 沉淀到 experience/issues | 经验文档 |

### 8.3 适用场景

**需求理解阶段**：
``` text
Survey → 浏览需求文档结构
Question → 提出澄清问题
Read → 深入理解需求细节
Recite → 向用户确认理解
Review → 沉淀需求理解笔记
```

**代码理解阶段**：
``` text
Survey → 扫描项目目录结构
Question → 识别核心类和关键方法
Read → 阅读核心代码逻辑
Recite → 向用户确认理解
Review → 沉淀代码理解笔记
```

**经验沉淀阶段**：
``` text
Survey → 浏览 experience/issues 目录
Question → 找到相关的历史经验
Read → 深入阅读经验文档
Recite → 应用到当前任务
Review → 更新或创建新的经验文档
```

### 8.4 与其他方法的关系

| 方法 | 关系 |
|------|------|
| **乔哈里窗** | SQ3R 用于扩大开放区 |
| **苏格拉底提问** | SQ3R 的 Question 步骤使用苏格拉底提问 |
| **情境记忆法** | SQ3R 的 Review 步骤使用情境记忆沉淀 |
| **联动检查** | SQ3R 的 Survey 步骤识别关联文件 |

## 九、流程执行要点

> **核心原理**：每个步骤都是协作节点，AI 必须输出，人类必须确认，形成闭环

### 9.1 设计原则

| 原则 | 说明 | 防错效果 |
|------|------|---------|
| **每个步骤都是协作节点** | AI 输出 → 人类确认，不是 AI 独自完成 | 避免方向错误 |
| **内部过程不作为独立步骤** | "理解"是内部过程，合并到"确认" | 避免流程冗余 |
| **必须有可见的输出物** | 每步必须有输出，缺少视为流程未完成 | 避免跳过步骤 |
| **顺序正确** | "确认"在"执行"之前，不能跳过 | 避免执行偏差 |

### 9.2 常见错误与预防

| 错误类型 | 表现 | 预防措施 |
|---------|------|---------|
| **跳过确认** | 直接执行，不确认理解 | 强制输出"需求理解复述" |
| **缺少输出** | 步骤执行但无可见输出 | 每步检查输出物 |
| **顺序错误** | 先执行后确认 | 按"确认→规划→执行→自检→沉淀"顺序 |
| **联动遗漏** | 修改代码但未更新关联文件 | 规划阶段输出联动检查清单 |

### 9.3 强制执行保障

| 保障机制 | 说明 |
|---------|------|
| **输出物强制** | 每步必须有输出，缺少视为流程未完成 |
| **顺序强制** | 不可越级执行，必须按顺序 |
| **确认强制** | 未确认不能进入下一步 |
