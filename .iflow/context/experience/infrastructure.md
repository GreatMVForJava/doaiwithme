# 基础设施设计经验

> **适用场景**: 新项目搭建、目录结构设计、规范制定
> **核心目的**: 避免过度设计、保持精简、便于AI理解

---

## 一、目录结构设计原则

### 1.1 按需创建，避免过度设计

| 原则 | 说明 |
|------|------|
| 不预先创建空目录 | 空目录增加认知负担 |
| 不预先创建索引 | 索引维护成本高，文件>5个再考虑 |
| 根据实际需求调整 | 不要为未来可能的需求设计 |

### 1.2 结构一致性

- 同一类型的目录应该有类似的结构
- 如果差异很大，说明设计有问题

### 1.3 删除文件的判断标准

| 情况 | 处理 |
|------|------|
| 内容重复 | 保留最完整的，删除其他 |
| 空目录 | 直接删除 |
| 未使用的模板 | 删除 |

---

## 二、文档组织方式

### 2.1 时间序列组织

- 格式：`YYYY-MM-DD-主题.md`
- 优点：按时间排序，便于查找
- 适用：问题记录、经验沉淀

### 2.2 主题组织

- 按主题分类，子目录结构
- 优点：相关文档集中
- 适用：主题总结、设计经验

---

## 三、Skills设计规范

### 3.1 Skills定位

Skills是一种组织形式，给AI使用的可复用能力：
- 文件命名：`{技能名称}-skill.md`
- 调用方式：AI → endpoint入口 → skills目录 → 执行步骤 → 返回结果

### 3.2 目录结构

``` text
skills/
├── SKILLS_SPEC.md（技能规范）
├── web-search-skill.md
├── context-search-skill.md
└── ...
``` text

### 3.3 技能描述规范

格式：`技能名称：技能功能，技能用途`

---

## 四、endPoint设计规范

### 4.1 endPoint定位

- 只定义入口点，不包含具体实现
- 调用流程：AI → endPoint → skills/经验文档
- 保持精简，避免膨胀

### 4.2 核心原则

| 原则 | 说明 |
|------|------|
| 简洁性 | 只包含核心流程，不放具体指令 |
| 流程性 | 定义"做什么"，不定义"怎么做" |
| 指导性 | 使用明确术语，减少歧义 |

---

## 五、常见问题

### Q1: 目录太深怎么办？

减少层级，控制在3层以内。

### Q2: 文档太多找不到？

创建索引，但文件数量>5时再考虑。

### Q3: endPoint越来越长？

定期精简，具体实现移到experience或skills。
