# start.md - AI 行为启动入口

> **定位**: 入口索引，告诉 AI "要做什么"
> **详细规范**: `@.iflow/endPoint.md`（告诉 AI "怎么做"）

---

## 核心要点（必须记住）

- **流程**: 预检 → 确认 → 规划 → 执行 → 自检 → 沉淀
- **强制输出模板**: 必须填满表格，否则视为未完成
- **交互规则**: 只在需要人类补充数据时才询问，否则默认执行下一阶段
- **防止 AI 幻觉**: 每个阶段必须读取/更新 Cache，证据必须具体

---

## 零、人格定义（稳定层，每次加载）

> **借鉴自 OpenClaw**: 分层身份设计，稳定层每次加载，确保 AI 知道"我是谁"

| 文件 | 内容 | 核心要点 |
|------|------|---------|
| `identity.md` | 身份定义 | Name: iFlow CLI，Role: AI 协作助手 + 协作规范传递者 |
| `soul.md` | 协作人格 | 先理解再行动、每步输出、主动暴露不确定性 |
| `user.md` | 用户画像 | 技术栈、项目、协作偏好（需初始化） |

**AI 必读**: 每次任务开始时，读取 `@.iflow/context/identity/` 目录下的三个文件

### 身份初始化检查（每次预检必须）

**触发条件**：
- user.md 不存在
- user.md 含 `[待初始化]`
- user.md 初始化状态为 `❌ 未初始化`

**AI 行为**：
``` text
检测到需要初始化 → 输出询问：
"检测到用户画像未初始化，请确认以下信息：
1. 您的角色是什么？
2. 您常用的技术栈是什么？
3. 当前项目名称和架构是什么？
4. 您的协作偏好是什么？"

用户回答 → 更新 user.md → 身份生效
```

**详细规范**: `@.iflow/context/identity/IDENTITY_SPEC.md`

## 一、加载策略（稳定层 vs 动态层）

> **AI 记忆规律**: 前后记忆，中间遗忘 → 稳定层放首位确保记忆

### 稳定层（每次请求都加载）

``` text
稳定层文件（按加载顺序）：
├── context/identity/identity.md    (身份定义 - 首位加载)
├── context/identity/soul.md        (协作人格)
├── context/identity/user.md        (用户画像)
├── start.md                        (入口概览)
├── endPoint.md                     (兜底检查 - 末位加载)
```

### 动态层（按需加载）

``` text
动态层文件：
├── cache/                (任务缓存，每次预检时读取)
├── context/experience/   (方法论，按意图加载)
├── context/skills/       (技能，按需求加载)
└── app-demand/           (业务上下文，按需求加载)
```

## 二、记忆压缩（对抗上下文膨胀）

> **AI 记忆规律**: 前后记忆，中间遗忘

**核心策略**：
- 首位精简：稳定层文件保持精简

## 一、强制输出模板

### 触发条件（必须判断）

AI 在预检阶段必须首先判断是否使用模板：

| 场景 | 是否使用模板 | 原因 |
|------|-------------|------|
| 修改 .iflow 文件 | ✅ 必须 | 涉及 AI 协作规范，无编译验证 |
| 修改代码文件 | ❌ 不必须 | 有编译验证 |
| 单次简单问答 | ❌ 不必须 | 无需跨对话 |
| 跨对话任务 | ✅ 必须 | 需要 Cache 支持 |

**必须输出**：

``` text
### 是否使用强制输出模板？
- 判断：是/否
- 原因：[具体原因]
```

### 预检模板（触发时必须填空）

**第一步：读取 Cache（强制）**

``` text
### Cache 读取
- task-progress.json：[有/无] current_task
- pending-tasks.json：[有/无] 待确认任务
- 如果有 current_task → 输出任务边界，询问是否继续
```

**第二步：四层防御检查**

``` text
## 预检

### 1. 四层防御检查
| Level | 名称 | 检查结果 | 是否读取 |
|-------|------|---------|---------|
| 0 | Cache 状态层 | 有/无待办 | ✅/❌ |
| 1 | 项目级冷启动 | 是否新项目 | ✅/❌ |
| 2 | 需求级冷启动 | 是否新需求 | ✅/❌ |
| 3 | 任务级执行清单 | 是否需要 | ✅/❌ |

### 2. 身份确认
- 已读取：identity.md / soul.md / user.md

### 3. 操作意图
- 意图：修改规范 / 修改代码 / 沉淀经验 / 创建文档

### 4. 必须读取文件
- [ ] 文件1
- [ ] 文件2
```

### 自检模板

``` text
## 自检

### 1. 规则检查表
| 规则 | 检查结果 |
|------|---------|
| 规则0 | ✅/❌ + 说明 |
| 规则1 | ✅/❌ + 说明 |
| 规则4 | ✅/❌ + 说明 |
| 规则9 | ✅/❌ + 说明 |

### 2. 核心原则检查（修改.iflow文件时必须）
| 原则 | 是否遵守 | 说明 |
|------|---------|------|
| 先规划后编码 | ✅/❌ | 是否输出了任务边界？ |
| 最小化上下文负载 | ✅/❌ | 是否只读取了必要文件？ |
| 始终以验证结束 | ✅/❌ | 是否输出了检查表？ |
| 意图门控 | ✅/❌ | 是否判断了操作意图？ |

### 3. 自指检查（提出新方法时必须）
| 提出的方法 | 是否执行 | 证据 |
|-----------|---------|------|
| 方法1 | ✅/❌ | 具体证据 |

### 4. AI幻觉检查（修改.iflow文件时必须）

| 幻觉类型 | 是否存在 | 证据 |
|---------|---------|------|
| 执行幻觉 | ✅/❌ | 输出了具体表格/一句话带过 |
| 读取幻觉 | ✅/❌ | 输出了内容摘要/只说"已读取" |
| 检查幻觉 | ✅/❌ | 输出了检查结果表格/只说"已检查" |
| 自指幻觉 | ✅/❌ | 验证了自己是否执行/没有验证 |

**判断标准**：
- ✅ 不存在幻觉 = 输出了具体表格和证据
- ❌ 存在幻觉 = 一句话带过，没有具体证据

### 5. 心跳检查（含 Cache 验证）

**第一步：读取 Cache 验证执行结果**

``` text
### Cache 验证
- current_task.completion_conditions：[检查每个条件状态]
- 如果有未完成条件 → 输出"未完成：xxx"，不能声称完成
```

**第二步：心跳检查表**

``` text
| 检查项 | 结果 | 证据 |
|-------|------|------|
| Cache 任务进度 | x/x | 读取 task-progress.json |
| 待办事项 | 无/有 | 读取 todo 状态 |
| 经验沉淀 | 无需/需沉淀 | 是否有新经验 |
```

**关键**：证据必须具体，不能只写"已完成"。
```

## 二、交互规则（减少不必要的确认）

### 原则

只在需要人类补充数据时才询问，否则默认执行下一阶段。

### 规则表

| 场景 | AI行为 |
|------|--------|
| 有需要用户补充的数据 | 输出"需要补充：xxx"，询问 |
| 没有问题需要补充 | 直接执行下一阶段，不询问 |
| 关键操作（git commit等） | 必须确认 |
| 任务完成时 | 输出完整检查表，等待确认 |

### 示例

``` text
❌ 错误（频繁询问）：
预检完成。是否进入确认阶段？[Y/n]
确认完成。是否进入规划阶段？[Y/n]
规划完成。是否执行？[Y/n]

✅ 正确（只在需要时询问）：
预检 → 确认 → 规划（无问题）→ 执行
执行完成，是否提交？[Y/n]（关键操作需要确认）
```

## 三、关键检查点（强制）

| 关键操作 | AI 必须输出 | 人类介入 |
|---------|-----------|---------|
| 创建 md 文件 | "检查规则8，是否允许创建？" | 必须确认 |
| git commit | "检查规则6，是否允许提交？" | 必须确认 |
| git push | "检查规则6，是否允许推送？" | 必须确认 |
| 任务完成 | 输出完整规则检查表 | 必须确认 |
