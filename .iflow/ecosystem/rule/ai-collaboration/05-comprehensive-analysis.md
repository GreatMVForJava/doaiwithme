# 多维度分析框架

## 规则 5：全面分析规范

**规则内容**：分析问题时必须多维度全面分析 → 从功能、性能、可读性、可维护性、命名等维度分析 → 思想：避免遗漏重要问题，确保分析完整性

## 目的

确保在分析问题时，从多个角度全面分析，避免遗漏重要问题。

## 分析维度

### 1. 功能维度

**检查问题**：
- 是否解决了核心问题？
- 是否考虑了边界情况？
- 是否考虑了异常情况？

**示例**：
- OCR 回调处理：是否考虑了回调失败的情况？
- 工作流执行：是否考虑了节点执行失败的情况？

### 2. 性能维度

**检查问题**：
- 是否考虑了性能问题？
- 是否存在性能瓶颈？
- 是否需要优化？

**示例**：
- 数据库查询：是否需要添加索引？
- 并发处理：是否需要优化并发策略？

### 3. 可读性维度

**检查问题**：
- 代码是否易于理解？
- 命名是否清晰？
- 注释是否充分？

**示例**：
- 变量命名：是否使用了有意义的命名？
- 方法命名：是否使用了一致的命名风格？

### 4. 可维护性维度

**检查问题**：
- 代码是否易于维护？
- 是否遵循了设计原则？
- 是否存在技术债务？

**示例**：
- 代码结构：是否遵循了 DDD 规范？
- 依赖关系：是否遵循了依赖倒置原则？

### 5. 命名维度

**检查问题**：
- 是否存在命名混淆？
- 是否使用了成对命名？
- 是否遵循了命名规范？

**示例**：
- 节点命名：是否使用了 BEGIN/END 而不是 START/END？
- 参数命名：是否避免了与常量命名的混淆？

## 分析流程

### 步骤 1：理解问题

- 明确问题的核心是什么
- 确认问题的边界和上下文
- 理解问题的业务背景

### 步骤 2：多维度分析

从以下维度分析问题：
1. 功能维度
2. 性能维度
3. 可读性维度
4. 可维护性维度
5. 命名维度

### 步骤 3：主动询问

在提出方案前，主动询问用户：
- 是否有其他角度需要考虑？
- 是否有其他需求或约束？
- 是否有其他优先级？

### 步骤 4：自我检查

在提出方案前，进行自我检查：
- 是否遗漏了重要的维度？
- 是否考虑了所有边界情况？
- 是否遵循了项目规则和规范？

## 示例

### 示例 1：OCR 回调处理问题

**问题**：OCR 回调成功后，后续节点无法读取 data_format 节点的 outputSnapshot

**分析**：
- 功能维度：是否解决了核心问题？✅ 是
- 性能维度：是否考虑了性能问题？✅ 是（避免重复执行节点）
- 可读性维度：代码是否易于理解？✅ 是（添加了注释）
- 可维护性维度：是否遵循了设计原则？✅ 是（遵循了 DDD 规范）
- 命名维度：是否存在命名混淆？❌ 否（START 节点和 startNodeId 参数混淆）

**主动询问**：
- 是否有其他角度需要考虑？
- 是否有其他需求或约束？

**自我检查**：
- 是否遗漏了重要的维度？❌ 是（遗漏了命名维度）
- 是否考虑了所有边界情况？✅ 是
- 是否遵循了项目规则和规范？✅ 是

**改进**：
- 将 START 节点改名为 BEGIN，避免命名混淆
- 添加命名语义规范（规则 30）
