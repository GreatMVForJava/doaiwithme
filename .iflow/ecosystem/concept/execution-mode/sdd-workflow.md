# Spec 驱动开发（SDD）流程

> **定位**: 一种用 Spec 文档作为 AI 与人"契约"的开发方法论
> **来源**: 内化自《Spec 驱动开发（SDD）流程总结》
> **L2 引用**: @.iflow/ecosystem/rule/ai-collaboration/AI_COLLABORATION_SPEC.md

---

## 核心要点（必须记住）

- **SDD定义**：用 Spec 文档作为 AI Agent 与人类开发者之间的"契约"
- **两阶段**：拆解阶段（PRD→spec→plan→tasks）+ 执行阶段（AI自动推进）
- **三件套**：spec.md（功能规格）+ plan.md（技术方案）+ tasks.md（任务列表）
- **核心原则**：AI 不猜测、不发散，严格按照 Spec 执行
- **验收标准**：以测试结果和任务状态为准，不以"看起来完成"为准

---

## 核心概念

**SDD（Spec-Driven Development）**：用 Spec 文档作为 AI Agent 与人类开发者之间的"契约"，实现需求 → 规格 → 方案 → 任务 → 自动执行的端到端闭环。

**核心理念**：
- AI 不猜测、不发散，严格按照 Spec 执行
- 以测试结果和任务状态为准，不以"看起来完成"为准

---

## 两阶段流程

```
阶段一：拆解阶段（人 + AI 协作）
┌─────────────────────────────────────────────┐
│  PRD → spec.md → plan.md → tasks.md         │
│  （需求）（功能规格）（技术方案）（任务列表）  │
└─────────────────────────────────────────────┘
                    │
                    ▼
阶段二：执行阶段（AI Agent 自动推进）
┌─────────────────────────────────────────────┐
│  按 tasks.md 逐个实现 → 测试 → 标记完成      │
└─────────────────────────────────────────────┘
```

## 三件套详解

### 1. spec.md（功能规格）

| 章节 | 内容 | AI 执行要点 |
|------|------|------------|
| 问题陈述 | 解决什么问题？用户是谁？ | 明确范围边界 |
| 功能性需求 | FR-1, FR-2... 含用户故事 + 验收标准 | 每项可测试 |
| 非功能性需求 | 性能、安全、兼容性 | 有量化指标 |
| 不做什么 | 明确排除的范围 | 避免发散 |

### 2. plan.md（技术方案）

| 章节 | 内容 | AI 执行要点 |
|------|------|------------|
| 架构分层 | 模块划分、依赖关系 | 遵循现有架构 |
| 技术选型 | 框架、库、工具 | 复用现有技术栈 |
| 风险与回滚 | 可能的问题、回滚方案 | 提前预案 |

### 3. tasks.md（任务列表）

```markdown
## 任务列表

- [ ] T1: 任务名称
  - 依赖: 无
  - 验收标准: ...
  - 预估影响文件: ...
  
- [ ] T2: 任务名称
  - 依赖: T1
  - 验收标准: ...
```

---

## 最小验收标准（DoD）

一次"跑通 SDD"至少满足：

| 检查项 | 合格标准 |
|-------|---------|
| 三件套完整 | spec.md / plan.md / tasks.md 都存在 |
| 任务可执行 | 至少一个任务完成且有对应测试结果 |
| 状态已更新 | tasks.md 从 `[ ]` 更新为 `[x]` |
| 测试通过 | 无新增已知阻塞问题 |
| 变更可回滚 | 能明确说明回滚方式 |

---

## 常见卡点与处理

| 卡点 | 处理建议 |
|------|---------|
| 需求过大 | 缩到"半天可交付"的范围再拆解 |
| 任务粒度过粗 | 拆成可独立验收的小任务 |
| 执行中反复失败 | 先修复当前失败任务，不并行推进 |
| 测试不稳定 | 处理测试隔离与外部依赖控制 |
| 上下文混乱 | 拆解、执行、测试修复分不同对话进行 |

## 与文档工程的关系

| SDD 概念 | 文档工程对应 |
|---------|-------------|
| Spec 文档 | `.iflow/` 中的概念、规范、经验 |
| 契约 | 规范文件（规则、约束） |
| 验收标准 | AI 执行检查 |
| 不做什么 | 红线约束 |

**关键洞察**：`.iflow/` 文档工程本身就是一种 Spec 驱动的实践——用文档规范 AI 的行为边界。

---

## AI 执行检查

| 检查项 | 合格标准 | 不合格示例 |
|-------|---------|-----------|
| **Spec 意识** | 执行前确认规范/任务定义清晰 | 无 Spec 直接开始编码 |
| **收敛意识** | 按 Spec 执行，不发散 | 擅自添加未规划的功能 |
| **验收意识** | 以测试结果为准，不以"看起来完成"为准 | 跳过测试声称完成 |
| **状态更新** | 任务完成后更新状态标记 | 口头完成无状态更新 |

**AI自检模板**：

```text
### SDD 执行检查
| 检查项 | 是否合格 | 说明 |
|-------|---------|------|
| Spec 意识 | ✅/❌ | 是否有清晰的规范/任务定义: ... |
| 收敛意识 | ✅/❌ | 是否严格按 Spec 执行: ... |
| 验收意识 | ✅/❌ | 是否以测试结果为准: ... |
| 状态更新 | ✅/❌ | 是否更新任务状态: ... |
```
