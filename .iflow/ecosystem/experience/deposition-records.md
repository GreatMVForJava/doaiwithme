# deposition-records.md - 经验沉淀记录

> **定位**: AI 犯错案例与解决方案的沉淀记录（孵化器）
> **适用场景**: AI 需要参考历史经验、避免重复犯错
> **核心原则**: 沉淀是孵化器，成熟后迁移删除。协作核心部分应该"一开始就遵守"，而不是"事后查阅"

---

## 核心要点（必须记住）

- **沉淀定位**: 孵化器，不是墓地
- **沉淀价值**: 记录新发现的问题，成熟后固化到规范
- **固化原则**: 协作核心、重复犯错的内容 → 固化到 start.md / endPoint.md / 规则中
- **固化判断**: AI是否能在执行时遵守，不重复犯错

---

## 触发场景（何时记录）

| 场景 | 触发条件 | 记录类型 | 记录时机 |
|------|---------|---------|---------|
| **操作失败** | 命令/操作失败 | ERROR | 立即记录 |
| **用户修正** | 用户说"不对..."、"其实..." | LEARNING | 立即记录 |
| **功能缺失** | 用户想要但项目没有的功能 | FEATURE_REQUEST | 立即记录 |
| **工具失败** | 外部 API 或工具失败 | ERROR | 立即记录 |
| **知识过期** | 发现知识过期或错误 | LEARNING | 任务完成后检查 |
| **方法改进** | 发现更好的方法 | LEARNING | 任务完成后检查 |

---

## SPEC 规范

### 文档规范

| 要求 | 说明 |
|------|------|
| **格式统一** | 每个沉淀必须有"场景标签 + 场景描述 + 解决方案" |
| **场景标签** | 使用 `#标签1` `#标签2` 格式，便于检索 |
| **内容真实** | 只记录当前项目实际发生过的问题和解决方案 |
| **版本记录** | 每次更新记录日期和版本号 |

### 沉淀格式模板

```markdown
### 沉淀 N: 标题

**场景标签**: `#标签1` `#标签2` `#标签3`

**场景描述**: 
描述具体的业务场景和上下文

**解决方案**:
描述如何解决这个问题

**关键洞察**: 一句话总结核心经验
```

### 维护规范

| 规则 | 说明 |
|------|------|
| **新增沉淀** | 在末尾追加，编号递增 |
| **更新沉淀** | 在原文修改，更新版本日期 |
| **固化迁移** | AI不重复犯错 → 固化到规范 → 删除沉淀 |
| **索引同步** | 新增/删除沉淀时更新场景标签索引 |

**核心原则**：沉淀是孵化器，成熟后必须迁移删除。

### 沉淀18: 内化评估必须检查AI可执行性

**场景标签**: `#内化评估` `#可执行性` `#跨AI协作` `#skill调用`

**场景描述**:
评估文章内容是否值得内化到 .iflow 时，犯了四个错误：
1. **定位不清**：没有理解 issues/ 的定位是"孵化器"，不是"运行时护栏"
2. **模式混淆**：没有区分"被动投喂"和"主动获取"两种模式
3. **冗余判断失误**：没有检查现有机制是否已经完整
4. **未调用 skill**：概念不清时没有调用 context-search-skill 搜索项目内知识

**错误示例**:
| 内化建议 | 错误原因 |
|---------|---------|
| GUARDRAILS 触发器+防御指令 | 概念混淆，issues/ 是孵化器，不是运行时护栏 |
| 澄清机制示例 | 冗余，endPoint.md 2.2 已有完整触发条件和询问方式 |
| 词元经济学：差分隔离投喂 | 模式不同，.iflow 是主动获取，无需差分投喂 |

**解决方案**:
内化评估前必须执行：
1. **调用 skill**：概念不清时调用 `context-search-skill` 搜索项目内知识
2. **定位匹配**：内容与现有机制定位一致吗？
3. **模式匹配**：内容与工程模式一致吗？（主动获取 vs 被动投喂）
4. **冗余检查**：现有机制是否已经完整覆盖？

**已固化**: method-index.md 19.1.1 AI可执行性检查

**关键洞察**: 
- **概念不清时必须调用 skill**，不能直接判断
- **为了内化而内化**是最大陷阱，必须检查现有机制是否已覆盖
- .iflow 是主动获取模式，不是被动投喂模式

### 沉淀19: 全量文档审计的执行方法

**场景标签**: `#文档审计` `#全量修改` `#术语统一` `#Cache跟踪`

**场景描述**:
用户要求修改 `.iflow/` 下所有文件的被动描述（"加载"、"注入"、"投喂"）为主动描述（"读取"、"主动获取"）。涉及 69 个 .md 文件，需要系统化执行。

**解决方案**:
采用八步审计流程（已固化到 `document-audit-skill.md`）：
1. **明确目标**：确认范围、关键词、修改规则、保留规则
2. **获取清单**：`glob` 获取所有目标文件
3. **搜索匹配**：`search_file_content` 搜索目标词汇
4. **分类整理**：区分"需要修改"、"技术术语"、"无匹配"
5. **记录进度**：使用 Cache 记录审计进度
6. **逐个修改**：按 Cache 顺序修改
7. **输出清单**：按目录层级输出完整清单
8. **沉淀经验**：记录方法和发现的问题

**技术术语判断标准**：
| 类别 | 是否修改 | 示例 |
|------|---------|------|
| 编程模式 | ❌ 保留 | 构造器注入、依赖注入 |
| 安全术语 | ❌ 保留 | SQL注入、XSS注入 |
| 浏览器技术 | ❌ 保留 | 动态加载、页面加载 |
| AI协作模式 | ✅ 修改 | 文档注入→主动获取 |

**已固化**: `skills/document-audit-skill.md`

**关键洞察**:
- **技术术语必须保留**，不能一刀切修改
- **Cache 跟踪进度**是大量文件修改的关键
- **按目录层级输出**确保用户确认完整性
- 区分"行业标准术语"和"AI协作模式描述"

### 沉淀20: 复杂任务计时检查机制

**场景标签**: `#计时检查` `#复杂任务` `#自检` `#质量保证`

**场景描述**:
执行复杂任务（全量操作、多文件修改、跨目录任务）时，AI 往往执行时间过短，导致遗漏或深度不足。用户指出："每次让你全量执行的时候，你都没有很好的执行，你是不是应该有个计时功能？"

**解决方案**:
在 `endPoint.md` 和 `document-audit-skill.md` 中增加计时检查机制：
1. **计时开始**：复杂任务开始时记录 startTime 到 Cache
2. **计时结束**：任务结束时记录 endTime，计算 duration
3. **自检触发**：duration < 30分钟时，执行自检清单
4. **审计记录**：将计时结果和自检结论写入 Cache

**自检清单**：
| 检查项 | 说明 |
|-------|------|
| 是否遗漏文件？ | 全量任务是否每个文件都处理了？ |
| 是否深度不足？ | 是否只是简单替换，没有结合文档定位？ |
| 是否遗漏检查？ | 技术术语判断是否充分？ |
| 是否遗漏输出？ | 按目录层级的完整清单是否输出？ |

**已固化**: `endPoint.md` 核心要点 + 4.1.1节，`document-audit-skill.md` 步骤0和步骤9

**关键洞察**:
- **复杂任务执行时间远低于预估时间往往意味着遗漏或深度不足**
- **AI 应根据任务复杂度自评估所需时间**，而非硬编码固定值
- **计时检查是质量保证的最后一道防线**

### 沉淀21: 自指检查必须在执行时验证

**场景标签**: `#自指检查` `#计时机制` `#自检` `#方法执行`

**场景描述**:
用户要求执行文档质量审计时，AI 定义了"复杂任务计时检查"机制，但在实际执行时：
1. startTime 使用了硬编码时间 `"2026-03-24T13:00:00"`，而非获取实际时间
2. endTime 同样使用了硬编码时间
3. 没有验证自己是否真正执行了提出的方法

用户指出："开始时间和结束时间为什么没有？"

**问题根源**：
- 定义了机制，但执行时走形式
- 自检时只检查了"是否输出"，没有检查"是否真正执行"

**解决方案**：
1. **自指检查必须在执行时验证**：提出方法 → 执行方法 → 验证执行 → 记录证据
2. **时间必须使用实际值**：使用 `date` 命令获取实际时间，不能硬编码
3. **自检表格增加"是否真正执行"列**：不只检查"是否输出"

**自指检查模板**：

| 提出的方法 | 是否输出 | 是否真正执行 | 证据 |
|-----------|---------|-------------|------|
| 计时开始 | ✅ 输出了 | ❌ 硬编码时间 | 应使用 `date` 命令 |

**已固化**: endPoint.md 核心要点 + document-audit-skill.md

**关键洞察**:
- **自指检查是最容易遗漏的检查**
- **定义方法不等于执行方法**
- **输出形式不等于真正执行**

### 沉淀22: 概念内化必须服务于沟通一致性

**场景标签**: `#概念内化` `#沟通一致性` `#定位清晰` `#AI可执行` `#现有文档`

**场景描述**:
用户要求内化 "self-improving-agent" 概念。AI 直接搜索外部资料，创建了概念文件，犯了四个错误：
1. **定位不清**：没有理解 concept/ 的核心定位是"帮助我们沟通达成一致"，不是"知识库"
2. **可执行性未验证**：Self-Evolving Loop 需要 Evals 基础设施、LLM-as-Judge，我们没有
3. **已有替代未检查**：`deposition-records.md` 已经是简化版自我改进机制
4. **未看现有文档**：COMMANDS.md 已有完整的内化指令，却新建了重复文件

**错误本质**：
- 把 concept/ 当成了"知识仓库"
- 看到"新概念"就想内化
- 没有问"这个概念能帮助我们沟通什么？"
- 没有先看现有文档结构

**解决方案**：
概念内化前必须：
1. **先看现有文档**：COMMANDS.md 已有内化指令，先检查是否覆盖
2. **内化评估三问**：
   - 我们有沟通歧义吗？
   - 我们有能力执行吗？
   - 现有机制已覆盖吗？
3. **补充而非新建**：有价值的点补充到现有文件，而不是新建

**判断标准**：

| 问题 | 是 | 否 |
|------|-----|-----|
| 我们有沟通歧义吗？ | 可能需要内化 | 不需要内化 |
| 我们有能力执行吗？ | 可以内化 | 不应该内化 |
| 现有机制已覆盖吗？ | 不需要内化 | 可以考虑 |

**关键洞察**: 
- **concept/ 的核心定位是"沟通一致性"，不是"知识库"**
- **外部知识 ≠ 我们需要的概念**
- **为了内化而内化是最大陷阱**
- **先看现有文档，补充而非新建**

### 沉淀26: 删除代码前必须评估是否核心机制并询问确认

**场景标签**: `#删除操作` `#核心机制` `#询问确认` `#回退机制` `#完整性检查`

**场景描述**:
改造工作流架构时，AI 删除了 `WorkflowCallbackService` 等回调相关代码，理由是"新架构是同步执行"。但实际上：
1. **OCR/LLM 是异步调用**：回调机制是核心，删除后无法获取异步结果
2. **没有识别核心机制**：回调是连接异步调用和后续流程的桥梁
3. **没有询问确认**：直接删除，没有问用户是否需要保留
4. **建议不合理的替代方案**："手动或定时任务"，破坏了异步流程

**错误本质**：
- 删除前没有评估依赖关系
- 没有识别核心机制
- 没有询问就自行决定

**推广到所有情况**：

| 触发条件 | 必须执行 | 示例 |
|---------|---------|------|
| 删除任何代码文件 | 评估是否核心机制 | 回调服务是异步流程核心 |
| 删除接口/服务 | 检查调用链是否完整 | WorkflowCallbackService 被 OCR/LLM 回调使用 |
| 删除数据结构 | 检查是否影响数据流转 | NodeDefinition 是节点定义核心 |
| 提出替代方案 | 必须完整可行 | "手动触发"不是完整方案 |

**删除前评估清单**：

| 检查项 | 检查方法 | 不合格处理 |
|-------|---------|-----------|
| 是否被其他代码调用？ | 搜索 import 引用 | 有调用 → 不能删除 |
| 是否是流程关键节点？ | 分析数据流向 | 关键节点 → 不能删除 |
| 删除后是否有替代方案？ | 设计替代方案 | 无替代 → 不能删除 |
| 替代方案是否完整？ | 验证完整性 | 不完整 → 询问用户 |

**解决方案**：
删除代码前必须：
1. **搜索引用**：`search_file_content` 搜索 import 和类名引用
2. **分析数据流**：画出删除项在数据流中的位置
3. **评估核心性**：是否是流程关键节点？
4. **设计替代方案**：删除后如何保持功能完整？
5. **询问确认**：不确定时必须询问用户

**关键洞察**:
- **删除 ≠ 清理，删除是破坏性操作**
- **核心机制识别是删除前必须的检查**
- **不确定时必须询问，不能自行决定**
- **替代方案必须完整可行，不能是半成品**
