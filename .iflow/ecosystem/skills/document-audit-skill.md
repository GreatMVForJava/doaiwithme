# Document Audit Skill

## 使用场景

| 场景 | 用户意图 | 示例 |
|------|---------|------|
| 词汇统一 | 统一术语表达 | "把所有'加载'改成'读取'" |
| 格式规范 | 统一文档格式 | "检查所有文档的标题格式" |
| 概念修正 | 修正错误概念 | "把被动描述改为主动描述" |
| 全量扫描 | 遍历所有文件 | "需要修改@.iflow/ 下的所有文件" |

## 触发条件

- 用户要求修改目录下所有文件
- 用户要求遍历检查文档
- 用户说"全量"、"所有文件"、"遍历"

## 执行流程

### 步骤 0：计时开始（复杂任务必须）

**触发条件**：全量操作、多文件修改（>10个文件）、跨目录任务

**时间预估方法**（AI 自评估）：

| 任务复杂度 | 预估方法 | 示例 |
|-----------|---------|------|
| 文件数量 | 文件数 × 单文件处理时间 | 69文件 × 2分钟 = 138分钟 |
| 处理深度 | 简单替换 < 结合定位 < 重写 | 重写需要更多时间 |
| 分类判断 | 是否需要区分技术术语 | 分类判断增加时间 |
| 输出整理 | 是否需要完整清单输出 | 清单输出需要时间 |

``` json
// 记录到 Cache
{
  "task": "审计任务名称",
  "estimatedTime": "120min",
  "startTime": "2026-03-24T10:00:00",
  "status": "in_progress"
}
```

### 步骤 1：明确审计目标

**必须向用户确认**：
- 审计范围：哪个目录？哪些文件类型？
- 审计内容：搜索什么关键词/模式？
- 修改规则：匹配项如何修改？
- 保留规则：哪些不需要修改？

### 步骤 2：获取文件清单

```bash
# 使用 glob 获取所有目标文件
glob(pattern="**/*.md", path="/path/to/directory")
```

### 步骤 3：搜索匹配项

```bash
# 使用 search_file_content 搜索目标词汇
search_file_content(pattern="加载|注入|投喂", path="/path/to/directory", context=1)
```

### 步骤 4：分类整理

将匹配结果分类：
- ✅ **需要修改**：符合修改规则的匹配项
- ⏸️ **技术术语**：属于技术标准术语，保留不修改
- ⭕ **无匹配**：文件中没有目标词汇

### 步骤 5：记录进度

**必须使用 Cache 记录进度**：
```json
{
  "task": "审计任务名称",
  "status": "in_progress",
  "progress": {
    "total": 0,
    "completed": 0
  },
  "completed": [],
  "pending": [],
  "noNeedModify": []
}
```

### 步骤 6：逐个修改

- 按 Cache 记录的顺序逐个修改
- 修改前读取文件内容
- 修改后更新 Cache 进度
- 使用 `replace` 工具精确修改

### 步骤 7：输出完整清单

**按目录层级输出**：
```
目录/
├── file1.md          ✅ 已修改: 具体内容
├── file2.md          ⭕ 无匹配
└── subdir/
    ├── file3.md      ⏸️ 保留: 技术术语
    └── file4.md      ✅ 已修改: 具体内容
```

### 步骤 8：沉淀经验

将审计方法沉淀到 `deposition-records.md`

### 步骤 9：计时结束与自检（复杂任务必须）

**触发条件**：执行了步骤0的任务

``` json
// 更新 Cache
{
  "task": "审计任务名称",
  "estimatedTime": "120min",
  "startTime": "2026-03-24T10:00:00",
  "endTime": "2026-03-24T10:25:00",
  "duration": "25min",
  "timeSufficient": false
}
```

**自检清单**（duration < estimatedTime 时必须执行）：

| 检查项 | 说明 |
|-------|------|
| 是否遗漏文件？ | 全量任务是否每个文件都处理了？ |
| 是否深度不足？ | 是否只是简单替换，没有结合文档定位？ |
| 是否遗漏检查？ | 技术术语判断是否充分？ |
| 是否遗漏输出？ | 按目录层级的完整清单是否输出？ |

**关键洞察**: 复杂任务执行时间远低于预估时间往往意味着遗漏或深度不足，**必须自检**。

## 技术术语判断标准

| 类别 | 示例 | 是否修改 |
|------|------|---------|
| 编程模式 | 构造器注入、依赖注入、@Autowired注入 | ❌ 保留 |
| 安全术语 | SQL注入、XSS注入 | ❌ 保留 |
| 浏览器技术 | 动态加载、页面加载 | ❌ 保留 |
| 框架术语 | Spring注入、MCP注入 | ❌ 保留 |
| AI协作模式 | 文档注入、上下文注入 | ✅ 修改 |

**判断原则**：
- 是否是**行业标准术语**？→ 保留
- 是否是**代码实现细节**？→ 保留
- 是否是**AI协作模式描述**？→ 修改

## 输出格式模板

### 统计摘要

| 状态 | 数量 | 说明 |
|------|------|------|
| ✅ 已修改 | N | 符合修改规则 |
| ⭕ 无匹配 | N | 无目标词汇 |
| ⏸️ 保留 | N | 技术术语 |

### 技术术语保留说明

| 术语 | 所在文件 | 不修改原因 |
|------|---------|-----------|
| 构造器注入 | file.md | Java 依赖注入模式 |

## 注意事项

1. **先搜索后修改**：不要猜测，必须先搜索确认
2. **Cache 记录进度**：大量文件时必须使用 Cache 跟踪
3. **分类明确**：区分"需要修改"和"技术术语"
4. **按目录层级输出**：便于用户确认完整性
5. **沉淀经验**：完成后沉淀方法和发现的问题
6. **计时自检**：复杂任务必须预估时间，执行时间不足时自检
