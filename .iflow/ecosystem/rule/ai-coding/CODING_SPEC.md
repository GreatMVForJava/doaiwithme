# 编码规范

> **定位**: 定义代码质量、架构、风格的标准

---

## 核心要点（必须记住）

- **设计原则**：复用优先，以业务为核心，禁止 TODO 和 demo
- **代码架构**：禁止 @Autowired，禁止内部类，使用 @RequiredArgsConstructor
- **DDD规范**：硬编码改枚举，业务逻辑与存储分离
- **注释规范**：每个操作都要 Javadoc，禁止行尾注释
- **数据库幂等性**：save 方法必须实现幂等
- **修改完整性**：注释编号连续，变量命名一致，步骤完整
- **并发安全**：优先局部变量，ThreadLocal 必须在 finally 里 remove
- **命名语义**：文件名与占位符一致，使用领域语义明确的命名

---

## 一、设计原则规范

### 10. 设计原则
定义：重构和修改时以业务为核心，遵循复用优先原则 → 动作：能复用的复用，不能复用的修改，修改不了的新增，删除未使用内容 → 思想：以业务为核心确保代码符合领域语义，复用优先降低维护成本

### 11. 避免过度设计
定义：YAGNI（You Aren't Gonna Need It）原则是指不实现暂时不需要的功能 → 动作：禁止使用 demo 和 TODO，确保代码可直接使用 → 思想：TODO 缺少上下文而注释提供完整的依赖关系说明

### 12. 渐进式优化
定义：先实现基本功能，再逐步完善 → 动作：每次优化都要有明确的目标和验证方法 → 思想：渐进式优化避免一次性引入过多复杂性，小步快跑降低风险

## 二、代码架构规范

### 13. 代码组织规范
定义：代码组织的基本形式要求 → 动作：禁止使用 @Autowired 注入、内部类、路径类指定引用，使用 @RequiredArgsConstructor + final 字段、顶级类、import 导入 → 思想：构造器注入保证依赖不可变，顶级类符合 DDD 聚合根设计

### 14. 废弃的类
定义：废弃的类存在安全风险和技术债务 → 动作：废弃的类不允许使用，需要进行替换引用 → 思想：必须及时迁移，避免潜在问题

### 15. DDD规范
定义：DDD（Domain-Driven Design，领域驱动设计）核心是确定面向对象和确定业务边界 → 动作：符合 DDD 规范的内容修改硬编码为枚举，单次使用的硬编码使用常量类，存储层只负责数据持久化，业务逻辑层只负责业务逻辑 → 思想：数据库只是业务数据长期存储的介质

### 16. 使用 Lombok
定义：Lombok 是 Java 样板代码减少工具，通过注解自动生成 getter/setter/构造器等方法 → 动作：每个类都要用 Lombok 依赖，包括 @Data, @RequiredArgsConstructor, @Builder 等 → 思想：减少样板代码，提高可维护性

### 17. 注释规范
定义：注释是代码的一部分，帮助理解设计意图和边界 → 动作：每一个操作都需要按规范写好注释，包括创建原因、使用场景、设计思想、对应边界，禁止使用行尾注释，以行间注释说明 → 思想：Java 使用 Javadoc，Python 使用 Docstring，JavaScript 使用 JSDoc，按语言规范执行

### 18. 配置管理
定义：配置集中管理便于环境切换和统一维护 → 动作：外部服务的 URL 和路径必须通过配置类统一管理，配置类管理域名和路径常量，提供便捷方法隐藏 URL 拼接逻辑 → 思想：避免散落的硬编码增加修改成本

## 三、JDK特性规范

### 19. JDK特性规范
定义：JDK（Java Development Kit）新特性可简化代码 → 动作：使用 JDK 17 新特性包括 Record、instanceof 模式匹配、switch 表达式、文本块；var 简化局部变量声明仅限类型显而易见的情况 → 思想：平衡可读性和简洁性，避免类型推断带来的歧义

## 四、代码质量规范

### 20. 数据库幂等性
定义：幂等性确保同一操作执行多次与执行一次结果相同 → 动作：数据库操作必须实现幂等性，save 方法根据主键是否存在自动选择 insert 或 update → 思想：适用于重试场景、分布式事务、消息消费

### 21. 变量使用
定义：减少变量数量，降低认知负担 → 动作：存量可用的变量必须使用已经存在的变量，修改变量名称必须全局修改所有引用 → 思想：避免不一致

### 22. 方法一致性
定义：确保方法可以正确解析 → 动作：检查方法签名，确保方法参数一致，修改方法时同步更新所有调用点 → 思想：使用 var 时类型必须明确

### 23. 修改完整性
定义：修改代码或文档时必须保持格式和逻辑完整性 → 动作：注释编号连续，变量命名一致，表格/列表格式一致，修改前读取目标位置前后 5 行确认格式，同类内容同步修改 → 思想：修改完成后必须检查步骤是否完整、编号是否连续、格式是否一致

### 24. 不创建未使用的代码
定义：代码即债务，未使用的代码增加维护成本 → 动作：不创建未使用的代码，创建新类/方法必须添加详细注释说明 → 思想：保持代码精简

### 25. 并发安全
定义：在多线程环境下确保共享资源的线程安全 → 动作：优先使用局部变量，避免单例管理可变状态，禁止无界队列/缓存/Map，ThreadLocal 必须在 finally 里 remove() → 思想：防止内存溢出和数据串线

### 26. 接口参数校验规范
定义：DTO（Data Transfer Object，数据传输对象）负责外部接口参数转换和适配 → 动作：外部接口参数转换在 DTO 层处理，DTO 提供规范化方法，Service 层使用规范化方法 → 思想：外部接口参数格式不受控制，DTO 层降低对外部接口的依赖

### 27. 命名语义规范
定义：命名是代码的一部分，必须符合 DDD 规范 → 动作：避免命名混淆，使用领域语义明确的命名，文件名与占位符必须一致，使用成对命名避免混淆 → 思想：命名应该反映领域语义

### 28. 抽象方法设计规范
定义：抽象方法强制所有子类实现 → 动作：声明抽象方法时必须考虑所有可能的实现场景，如果某些子类不需要实现抽象方法，应该提供默认实现或使用接口 → 思想：避免强制实现导致不必要的代码

### 29. 禁止使用 @Lazy 掩盖设计问题
定义：@Lazy 不能解决根本问题 → 动作：禁止使用 @Lazy 注解和ApplicationContext方式掩盖循环依赖等设计问题，循环依赖表明架构设计有问题，必须通过架构重构解决 → 思想：用 @Lazy 掩盖设计问题等同于埋雷

## 五、代码风格规范

### 30. 代码风格规范
定义：避免 IDE 警告，保持代码格式一致性 → 动作：禁止悬空/重复的注释块和多余的空白行，每个注释块必须紧跟方法/类，同一方法只能有一个注释块 → 思想：字节码行数与源码行数一致
