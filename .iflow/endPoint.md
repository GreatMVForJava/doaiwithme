# endPoint.md - AI 执行规范

## 零、强制执行检查点

AI 必须依次输出以下内容，缺少任何一项视为流程未完成：

| 步骤 | 必须输出 | 格式要求 | 人机协作 |
|------|---------|---------|---------|
| **确认** | 需求理解复述 + 理解边界 | "我理解您需要..." | AI输出 → 人类确认 |
| **规划** | 联动检查清单 + 执行计划 | 表格形式 | AI输出 → 人类确认 |
| **执行** | 修改文件列表 + 编译结果 | 待办列表 + 状态 | AI输出 → 执行中反馈 |
| **自检** | RULE_SPEC.md 检查表 | 表格形式 | AI输出 → 人类确认 |
| **沉淀** | 文档更新路径 | 文件路径列表 | AI输出 → 人类确认 |

**执行流程图**：
```
确认 → [输出需求理解] → 用户确认？
                              ↓ 是
规划 → [输出检查清单+计划] → 用户确认？
                              ↓ 是
执行 → [输出修改列表+编译]
                              ↓
自检 → [输出检查表] → 用户确认？
                              ↓ 是
沉淀 → [输出文档路径] → 任务完成
```

## 一、使用时机

### 1.1 触发时机（何时使用）
- **任务开始前**：理解需求，复用历史经验，避免重复犯错
- **任务执行中**：检查任务结果，主动提问配合，确保任务偏差最小
- **任务完成后**：沉淀事实内容，便于迁移，降低边际成本

### 1.2 调用时机（何时调用各部分）
| 任务阶段       | 调用内容       | 触发条件          | 目的          |
|------------|------------|---------------|-------------|
| **任务开始前**  | 3.0 读取前序AI沉淀 | 存在前序任务 | 继承上下文，避免冷启动 |
| **任务开始前**  | 3.1 复用历史经验 | 收到任务请求        | 避免重复犯错，减少幻觉 |
| **需求理解阶段** | 3.2 主动提问配合 | 不理解概念/需求/发现矛盾/需要搜索信息/需要执行特定任务 | 确保理解准确，避免偏差，查找合适的 skills，执行实现步骤 |
| **需求理解阶段** | 3.3 确认需求理解 | 主动提问配合后 | 确认真正理解核心诉求 |
| **代码编写阶段** | 3.4 检查任务结果 | 编写代码/修改代码     | 确保符合规范，消除警告 |
| **任务完成后**  | 3.5 沉淀事实内容 | 任务完成/发现有价值内容  | 便于迁移，降低边际成本 |

### 1.3 使用流程（如何使用）
1. **任务开始前**：读取 endpoint.md → 执行 3.0 读取前序AI沉淀（如有）→ 执行 3.1 复用历史经验 → 理解需求
2. **需求理解阶段**：不理解时执行 3.2 主动提问配合（包括调用 skills 查找）→ 执行 3.3 确认需求理解
3. **代码编写阶段**：编写代码 → 执行 3.4 检查任务结果 → 确保质量
4. **任务完成后**：执行 3.5 沉淀事实内容 → 记录经验 → 更新目录

## 二、核心指导原则

确认→规划→执行→自检→沉淀

**确认** → 复述需求理解，说明理解边界；输出：需求理解复述；思想：确保方向正确，避免执行偏差

**规划** → 复用历史经验 + 联动检查 + 执行计划；输出：联动检查清单 + 执行计划；思想：磨刀不误砍柴工，遗漏是最大的风险

**执行** → 按计划修改代码，编译验证；输出：修改文件列表 + 编译结果；思想：按计划执行，不跳过步骤

**自检** → 对照规范逐项检查；输出：检查表；思想：作为最后防线，避免遗漏问题

**沉淀** → 更新 experience/issues；输出：文档更新路径；思想：降低边际成本，下次更快

### 2.1 人机协作原则

每个步骤都是**协作节点**，形成闭环：

| 步骤 | AI 输出 | 人类输入 | 协作类型 |
|------|---------|---------|---------|
| **确认** | 需求理解复述 + 理解边界 | 确认或纠正 | 双向确认 |
| **规划** | 联动检查清单 + 执行计划 | 确认方案或补充 | 双向确认 |
| **执行** | 修改代码、编译验证 | 执行中反馈（如有） | 单向输出 |
| **自检** | 检查表 | 确认或提问 | 双向确认 |
| **沉淀** | 更新 experience/issues | 确认沉淀内容 | 双向确认 |

### 2.1 组织形式原则

**简洁性原则**：endpoint 应该保持简洁，避免膨胀和重复
- 只包含核心流程、调用方式、兜底校验
- 不包含解释性内容、具体实现细节
- 解释性内容放在 experience/ 和 skills/ 目录下

**流程性原则**：endpoint 应该以流程为主，定义"做什么"
- 定义执行步骤、调用时机、触发条件
- 明确每个步骤的目的和内容
- 详细实施方法放在实施细则中

**指导性原则**：endpoint 应该提供明确的指导，减少歧义
- 使用清晰的章节编号（一、二、三...）
- 使用明确的术语和概念
- 核心步骤与实施细则一一对应

**层级性原则**：endpoint 应该从抽象到具体，层层递进
- 第一层：核心指导原则（继承→复用→检查→沉淀→配合）
- 第二层：核心步骤（6个核心步骤）
- 第三层：实施细则（对应核心步骤的详细方法）
- 第四层：沉淀格式（4种文档格式）

**可复用原则**：endpoint 的内容应该能够被其他 AI 复用
- 使用通用的术语和概念
- 避免项目特定的内容
- 具体的实现细节放在 experience/ 目录下

### 2.2 审慎程度分级

| 级别 | 文档 | 审慎程度 | 描述 |
|------|------|----------|------|
| 一级 | endpoint.md | 最重要 | AI 执行并减少幻觉的最后一道关卡，所有字词都要考究 |
| 二级 | skills/ | 次级重要 | 专业技能的抽象，需要反复斟酌 |
| 三级 | experience/ | 需要准确好用 | 经验，需要准确、好用，能够给下次任务使用，和其他 AI 使用 |

### 2.3 定位说明

| 文档 | 定位 | 作用 | 执行时机 |
|------|------|------|----------|
| endpoint.md | 核心兜底的入口 | 通过流程化、规范化的方式，调用所有能用的资源 | 任务开始前、执行中、完成后 |
| RULE_SPEC.md | 规范 | 规范 AI 的行为，每次修改之后都执行 | 每次修改后 |
| Context/ | 自助检验 | AI 可以自助地查看、选择、调用 | 对话级或会话级 |

## 三、核心步骤

### 3.0 确认需求理解
**必须输出**：需求理解复述 + 理解边界

**执行内容**：
- 复述用户需求："我理解您需要..."
- 说明理解边界：包含什么、不包含什么
- 识别模糊点：需要进一步确认的内容

**人机协作**：AI 输出理解 → 人类确认或纠正

### 3.1 规划（复用 + 联动检查 + 执行计划）
**必须输出**：联动检查清单 + 执行计划

**执行内容**：
- **复用历史经验**：
  - 读取 `.iflow/context/issues/` 是否有类似问题
  - 读取 `.iflow/context/experience/` 是否有相关经验
  - 读取需求目录下的冷启动文档（如存在）
- **联动检查**：
  - 识别数据流上下游
  - 识别共享概念
  - 识别文档同步
  - 输出联动检查清单（表格形式）
- **执行计划**：
  - 列出待修改文件
  - 列出待删除文件
  - 列出风险点

**人机协作**：AI 输出规划 → 人类确认方案

### 3.2 执行
**必须输出**：修改文件列表 + 编译结果

**执行内容**：
- 创建待办列表跟踪进度
- 按计划修改代码
- 编译验证
- 更新待办状态

**人机协作**：AI 输出执行结果 → 人类执行中反馈（如有）

### 3.3 自检
**必须输出**：检查表

**执行内容**：
- 对照 RULE_SPEC.md 和 ai-coding/CODING_SPEC.md 逐项检查
- 输出检查表（表格形式）
- 消除 IDE 警告
- 确认编译通过

**人机协作**：AI 输出自检结果 → 人类确认或提问

### 3.4 沉淀
**必须输出**：文档更新路径

**执行内容**：
- **问题记录**：`.iflow/context/issues/YYYY-MM-DD-问题类型.md`
- **设计经验**：更新 `.iflow/context/experience/collaboration-method.md`
- **索引更新**：更新 `.iflow/context/experience/EXPERIENCE_SPEC.md`

**人机协作**：AI 输出沉淀内容 → 人类确认

## 四、实施细则（对应核心步骤）

### 4.0 确认需求理解实施细则（对应 3.0）

**输出格式**：
``` text
## 需求理解确认

**核心诉求**：[一句话概括]

**理解边界**：
- 包含：[列出包含的内容]
- 不包含：[列出不包含的内容]

**模糊点**：
- [需要进一步确认的内容]

是否正确？
```

### 4.1 规划实施细则（对应 3.1）

**联动检查清单格式**：
``` text
## 联动检查清单

| 关联类型 | 关联文件 | 是否需同步 | 修改内容 |
|---------|---------|-----------|---------|
| 数据流上游 | | | |
| 数据流下游 | | | |
| 共享概念 | | | |
| 文档同步 | | | |
```

**执行计划格式**：
``` text
## 执行计划

### 待修改文件
- [ ] 文件路径1
- [ ] 文件路径2

### 待删除文件
- [ ] 文件路径1

### 风险点
- 风险点1：[描述]

是否确认执行？
```

**复用历史经验**：
- 读取 experience/issues 目录，提取相关经验
- 应用联动检查清单模板（见 `.iflow/context/experience/collaboration-method.md`）

### 4.2 执行实施细则（对应 3.2）

**待办列表格式**：
``` text
## 待办列表

| # | 任务 | 状态 |
|---|------|------|
| 1 | 修改文件A | ⏳ 进行中 |
| 2 | 修改文件B | ⏸ 待执行 |
| 3 | 编译验证 | ⏸ 待执行 |
```

**执行中反馈**：如遇到问题，及时向用户反馈

### 4.3 自检实施细则（对应 3.3）

| 规则31 | 未经允许不创建 md 文档 | ✅/❌ |
| 规则32 | 修改后自检 | ✅/❌ |

### CODING_SPEC.md（编码规范）
| 规则 | 要求 | 检查结果 |
|------|------|---------|
| 规则4 | 删除未使用内容 | ✅/❌ |
| 规则7 | 不使用 @Autowired，使用构造器注入 | ✅/❌ |

## 六、核心价值

### 6.1 强制执行保障
- 每步必须有输出物：缺少输出物视为流程未完成
- 每步都需要确认：人机协作形成闭环
- 不可跳过：按顺序执行，不可越级

### 6.2 减少遗漏
- 联动检查清单：规划阶段必须输出，避免遗漏关联文件
- 检查表：自检阶段必须输出，避免遗漏规范

### 6.3 人机协作闭环
- 确认阶段：AI 理解 → 人类确认
- 规划阶段：AI 规划 → 人类确认
- 执行阶段：AI 执行 → 人类反馈
- 自检阶段：AI 自检 → 人类确认
- 沉淀阶段：AI 沉淀 → 人类确认
