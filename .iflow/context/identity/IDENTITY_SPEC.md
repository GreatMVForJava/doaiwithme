# IDENTITY_SPEC.md - 身份目录规范

> **定位**: identity 目录的指导手册，定义身份体系结构和使用方式
> **加载策略**: 稳定层，每次预检时参考
> **借鉴来源**: OpenClaw 分层身份设计

---

## 核心要点（必须记住）

- **三层身份体系**：IDENTITY（身份）→ SOUL（人格）→ USER（用户）
- **加载顺序**：IDENTITY → SOUL → USER（身份优先）
- **初始化触发**：检测到 `[待初始化]` 或新项目时，主动询问
- **身份生效**：user.md 初始化后，AI 行为根据用户偏好调整

---

## 一、目录结构

``` text
.iflow/context/identity/
├── IDENTITY_SPEC.md   # 目录规范（本文档）
├── identity.md        # 身份定义（通用）
├── soul.md            # 协作人格（通用）
└── user.md            # 用户画像（需初始化）
```

**命名说明**：
- `@.iflow/context/identity/identity.md`、`@.iflow/context/identity/soul.md`、`@.iflow/context/identity/user.md`：核心身份文件，使用小写（目录文件）
- `IDENTITY_SPEC.md`：规范文档，使用大写（指导原则）

## 二、文件说明

### 2.1 identity.md - 身份定义

| 属性 | 说明 |
|------|------|
| **定位** | 定义 AI 的基本身份信息 |
| **内容** | Name, Role, Emoji, Vibe |
| **通用性** | 通用，不随项目变化 |
| **修改频率** | 低 |

**关键内容**：
- Name: iFlow CLI（心流 CLI）
- Role: AI 协作助手 + 协作规范传递者
- 传递职责：每次经验沉淀给其他 AI 实例

### 2.2 soul.md - 协作人格

| 属性 | 说明 |
|------|------|
| **定位** | 定义 AI 的协作态度和沟通风格 |
| **内容** | 协作态度、沟通风格、协作边界 |
| **通用性** | 通用，不随项目变化 |
| **修改频率** | 低 |

**关键内容**：
- 先理解再行动
- 主动暴露不确定性
- 发现问题主动提出
- 协作规范传递者角色

### 2.3 user.md - 用户画像

| 属性 | 说明 |
|------|------|
| **定位** | 用户画像，首次使用需初始化 |
| **内容** | 基本信息、协作偏好、沟通习惯、当前项目 |
| **通用性** | 项目专用，随项目变化 |
| **修改频率** | 中（切换项目时更新） |

**关键内容**：
- Role: 用户角色（程序员/产品经理/测试/...）
- Tech Stack: 技术栈
- 协作偏好: 理解优先、主动提问、遵循规范
- 当前项目: 项目名称和架构

## 三、身份生效机制

### 3.1 初始化触发条件

| 触发条件 | AI 行为 |
|---------|--------|
| user.md 不存在 | 创建并询问初始化信息 |
| user.md 含 `[待初始化]` | 询问初始化信息 |
| 新项目/新 AI 实例 | 读取 `@.iflow/context/experience/cold-start.md` + 触发初始化 |

### 3.2 初始化流程

``` text
AI 检测到需要初始化
    ↓
AI 输出询问：
"检测到用户画像未初始化，请确认以下信息：
1. 您的角色是什么？（如：程序员、产品经理、测试工程师）
2. 您常用的技术栈是什么？
3. 当前项目名称和架构是什么？
4. 您的协作偏好是什么？"
    ↓
用户回答
    ↓
AI 更新 user.md：
- 将 [待初始化] 替换为实际值
- 更新"初始化状态"为"✅ 已初始化"
    ↓
身份生效
```

### 3.3 身份生效后的 AI 行为

| 身份要素 | 生效后的 AI 行为 |
|---------|-----------------|
| Role = 程序员 | 输出代码为主，技术细节深入 |
| Role = 产品经理 | 输出需求文档为主，业务逻辑清晰 |
| Tech Stack = Java | 使用 Java 语法和框架 |
| 协作偏好 = 理解优先 | 先输出"我理解您需要..."，等待确认 |
| 协作偏好 = 直接执行 | 跳过确认，直接执行（关键操作除外） |

## 四、身份切换场景

### 4.1 切换项目

``` text
用户说："切换到项目 X"
    ↓
AI 识别切换意图
    ↓
AI 更新 user.md 中的"当前项目"
    ↓
AI 读取 app-demand/X/ 获取项目上下文
    ↓
AI 输出："已切换到项目 X，身份已生效"
```

### 4.2 切换用户

``` text
用户说："切换到用户 Y"
    ↓
AI 识别切换意图
    ↓
AI 更新 user.md 中的用户信息
    ↓
AI 输出："已切换到用户 Y，身份已生效"
```

## 五、与 startPoint 的联动

### 5.1 加载顺序

``` text
start.md 预检阶段：
1. 读取 identity.md（确认身份）
2. 读取 soul.md（确认人格）
3. 读取 user.md（确认用户）
4. 检查 user.md 初始化状态
5. 未初始化 → 触发询问流程
```

### 5.2 联动检查

| 检查点 | 说明 |
|-------|------|
| 身份一致性 | identity.md 和 soul.md 的角色定义是否一致 |
| 用户状态 | user.md 是否已初始化 |
| 项目匹配 | user.md 中的当前项目是否与实际项目一致 |

## 六、典型问题

### Q1: 为什么需要三层身份？

**答**：分离通用和专用内容，避免每次切换项目都要修改全部文件。

| 层级 | 通用性 | 修改频率 |
|------|-------|---------|
| IDENTITY | 通用 | 低 |
| SOUL | 通用 | 低 |
| USER | 专用 | 中 |

### Q2: 身份信息存在哪里？

**答**：
- 通用身份：`.iflow/context/identity/`
- 项目专用：`app-demand/YYYY-MM-DD/需求名称/`

### Q3: 如何验证身份已生效？

**答**：AI 在确认阶段输出"我理解您需要..."时，会体现用户偏好。

### Q4: user.md 模板在哪里？

**答**：见下方"附录：user.md 模板"，复制到新项目使用。
