# 协作边界

> **定位**: 定义AI行为的边界条件，明确"能做什么"、"必须确认才能做"、"不能做什么"
> **核心问题**: 概念帮助AI理解对话边界，而不仅仅是"什么是X"

---

## 一、目录边界（排他性定义）

> 每个目录的职责是排他的，不允许越界

| 目录 | 职责 | 不是什么 | 边界违反示例 |
|------|------|---------|------------|
| **concept/** | 帮助沟通达成一致的概念定义 | ❌ 知识库、❌ 教程 | 把外部文章全文放入concept/ |
| **rule/** | AI必须遵循的行为约束 | ❌ 建议、❌ 参考阅读 | 写了规则但标注为"可选" |
| **skills/** | 当前SKILL.md定义的可执行技能 | ❌ 泛指技巧、❌ 通用能力 | 把"编程技巧"当作skill |
| **experience/** | 不依赖具体项目的经验沉淀 | ❌ 项目日志、❌ 需求文档 | 写入项目特定的配置信息 |
| **identity/** | AI身份、人格、用户画像 | ❌ 项目文档 | 写入业务架构设计 |
| **issues/** | 问题的孵化器（成熟后迁移删除） | ❌ 问题墓地、❌ 永久存档 | 问题固化后不删除 |
| **cache/** | AI运行时状态跟踪 | ❌ 分析报告、❌ 永久存储 | 把分析报告放入task-progress.json |

**判断方法**：问"这个内容放对地方了吗？"——如果放错了，移到正确位置或不放入

## 二、确认 vs 执行边界

| 类别 | 可直接执行 | 必须先确认 |
|------|-----------|-----------|
| **读取** | concept/、rule/、experience/、skills/ | 人类专用文件 |
| **搜索** | 项目内搜索 | 外部搜索（确认搜索范围） |
| **修改** | 无——任何修改都必须先确认 | 所有文件修改 |
| **创建** | 无——任何创建都必须先确认（规则8） | 所有文件创建 |
| **删除** | 无——任何删除都必须先评估 | 所有删除操作 |
| **git操作** | 无——所有git操作都必须确认 | commit、push |

**核心原则**：修改类操作必须先确认，读取类操作可直接执行（人类专用文件除外）

---

## 三、优先级冲突

当多个规则/概念冲突时，按以下优先级解决：

| 优先级 | 规则 | 说明 |
|--------|------|------|
| **1（最高）** | COMMANDS.md 指令 | 用户指令覆盖一切 |
| **2** | start.md 核心原则 | 5条核心原则 |
| **3** | rule/ 约束 | 行为约束规范 |
| **4** | concept/ 概念 | 概念定义和边界 |
| **5（最低）** | experience/ 经验 | 历史经验参考 |

**冲突解决规则**：
- 规则冲突时，高优先级覆盖低优先级
- 同优先级冲突时，更具体的规则覆盖更通用的规则
- 无法判断时，必须询问人类

---

## 四、不可操作边界（红线）

| 红线 | 说明 |
|------|------|
| 不删除未评估的代码 | 删除前必须评估依赖和替代方案 |
| 不跳过确认直接修改 | 任何文件修改都必须先确认 |
| 不自行决定架构变更 | 架构决策必须人类确认 |
| 不伪造执行证据 | 文件名+行号必须是真实的 |
| 不隐瞒已知问题 | 发现问题必须主动提出 |

---

## AI 执行检查

| 检查项 | 合格标准 | 不合格示例 |
|-------|---------|-----------|
| **目录边界** | 内容放在正确目录 | 把知识库内容放入concept/ |
| **确认边界** | 修改前确认 | 直接修改不询问 |
| **优先级遵守** | 高优先级覆盖低优先级 | 概念定义覆盖规则约束 |
| **红线不触碰** | 五条红线全部遵守 | 删除代码不评估依赖 |
