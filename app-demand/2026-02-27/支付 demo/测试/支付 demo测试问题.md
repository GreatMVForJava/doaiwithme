## 支付流程问题

### P1: 微信支付回调偶发丢失

**问题描述**：
在高并发场景下，微信支付回调偶发丢失，导致订单支付成功但状态未更新。

**复现步骤**：
1. 模拟100并发支付请求
2. 检查订单状态
3. 发现部分订单仍为"待支付"

**根本原因**：
- 网络抖动导致回调请求丢失
- 回调处理超时，微信未收到成功响应

**解决方案**：
1. 增加主动轮询机制：支付后30秒未收到回调，主动查询微信订单状态
2. 增加消息队列缓冲：回调先入队，异步处理
3. 增加重试机制：回调处理失败自动重试3次

**预防措施**：
- 支付状态最终一致性设计
- 定时任务补偿（每分钟扫描待支付超时订单）

---

### P5: 支付金额精度丢失

**问题描述**：
支付金额使用浮点数存储，导致金额计算出现精度丢失。

**复现步骤**：
1. 订单金额 0.1 + 0.2
2. 期望结果 0.3
3. 实际结果 0.30000000000000004

**根本原因**：
- 使用 float/double 类型存储金额
- 浮点数二进制表示存在精度问题

**解决方案**：
1. 数据库使用 DECIMAL(10,2) 类型
2. Java 使用 BigDecimal 类型
3. 金额计算使用 BigDecimal 的 add/subtract/multiply 方法

**预防措施**：
- 代码审查时检查金额字段类型
- 禁止使用 float/double 存储金额

---

### P10: 支付超时订单状态不一致

**问题描述**：
用户支付过程中超时，订单状态与实际支付结果不一致。

**复现步骤**：
1. 用户发起支付
2. 网络超时
3. 订单状态仍为"待支付"，但实际已扣款

**根本原因**：
- 支付超时未正确处理
- 缺少超时补偿机制

**解决方案**：
1. 前端支付超时后主动查询订单状态
2. 后端增加超时订单定时任务，主动查询第三方状态
3. 提供订单状态查询接口，供用户主动刷新

**预防措施**：
- 所有支付操作增加超时处理
- 状态变更记录操作日志，便于追溯

## 并发控制问题

### P2: 并发场景下订单重复支付

**问题描述**：
同一订单被多次支付，导致用户资金损失。

**复现步骤**：
1. 同一订单发起两次支付请求
2. 两个请求同时到达
3. 两笔支付都成功

**根本原因**：
- 缺少幂等控制
- 分布式锁实现不完善

**解决方案**：

``` java
// 幂等Key设计
String idempotentKey = orderNo + ":" + channel + ":" + minute;
Boolean acquired = redis.setnx(idempotentKey, "1", 300); // 5分钟过期
if (!acquired) {
    throw new BusinessException("订单正在处理中");
}

// 分布式锁设计
RLock lock = redisson.getLock("ORDER_PAY_LOCK:" + orderNo);
try {
    if (lock.tryLock(30, 10, TimeUnit.SECONDS)) {
        // 处理支付逻辑
    }
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

**预防措施**：
- 所有写操作增加幂等校验
- 代码审查时检查并发控制逻辑

### P6: 分布式锁死锁问题

**问题描述**：
Redis 分布式锁在某些场景下出现死锁，导致后续请求全部阻塞。

**复现步骤**：
1. 获取锁后服务宕机
2. 锁未释放
3. 后续请求全部等待

**根本原因**：
- 锁未设置过期时间
- 异常情况下未正确释放锁

**解决方案**：

``` java
// 错误示例
jedis.set("lock", "1"); // 无过期时间，死锁风险

// 正确示例
jedis.set("lock", "1", "NX", "EX", 30); // 设置30秒过期

// 推荐使用 Redisson
RLock lock = redisson.getLock("myLock");
lock.lock(30, TimeUnit.SECONDS); // 自动过期
// 或使用看门狗机制
lock.lock(); // 默认30秒，自动续期
```

**预防措施**：
- 使用成熟的分布式锁框架（Redisson）
- 必须设置锁过期时间
- try-finally 确保锁释放

### P7: 秒杀场景库存超卖

**问题描述**：
秒杀活动中，库存被超卖，导致无法发货。

**复现步骤**：
1. 库存剩余1件
2. 100人同时下单
3. 100人都下单成功

**根本原因**：
- 库存扣减未加锁
- 数据库读写分离延迟

**解决方案**：

``` sql
-- 方案1：乐观锁
UPDATE goods SET stock = stock - 1 
WHERE id = ? AND stock > 0;
```

``` text
-- 方案2：Redis 预扣库存
Long stock = redis.decr("stock:" + goodsId);
if (stock < 0) {
    redis.incr("stock:" + goodsId); // 回滚
    throw new BusinessException("库存不足");
}
```

**预防措施**：
- 库存操作使用 Redis 原子操作
- 数据库增加库存校验约束
- 秒杀场景使用消息队列削峰

## 支付对账问题

### P3: 对账差异未自动处理

**问题描述**：
对账发现的差异未自动处理，需要人工逐条核实。

**复现步骤**：
1. 执行每日对账
2. 发现10笔差异
3. 需要人工逐条核实

**根本原因**：
- 缺少自动处理逻辑
- 差异分类不够细化

**解决方案**：

``` text
差异自动处理规则：
1. 时间差异（跨日交易）：自动延后处理
2. 手续费差异：自动记录，不做处理
3. 金额差异：标记为异常，人工处理
4. 本地有第三方无：主动查询第三方确认
5. 第三方有本地无：补录本地记录
```

**预防措施**：
- 建立差异自动处理规则
- 人工处理比例<5%

## 退款功能问题

### P4: 退款超时未自动重试

**问题描述**：
退款请求超时后未自动重试，导致用户长时间未收到退款。

**复现步骤**：
1. 发起退款请求
2. 网络超时
3. 退款状态未更新

**根本原因**：
- 缺少退款重试机制
- 超时异常未正确处理

**解决方案**：

``` java
// 退款重试机制
@Retryable(
    value = {RefundTimeoutException.class},
    maxAttempts = 3,
    backoff = @Backoff(delay = 1000, multiplier = 2)
)
public void refund(RefundRequest request) {
    // 退款逻辑
}

// 定时补偿任务
@Scheduled(cron = "0 */5 * * * ?")
public void retryFailedRefunds() {
    List<RefundOrder> failedRefunds = refundOrderMapper.selectFailedRefunds();
    for (RefundOrder refund : failedRefunds) {
        refundService.retry(refund);
    }
}
```

**预防措施**：
- 关键操作增加重试机制
- 定时任务补偿失败订单

### P9: 重复退款风险

**问题描述**：
同一订单被多次退款，造成资金损失。

**复现步骤**：
1. 订单已退款
2. 再次发起退款请求
3. 退款成功

**根本原因**：
- 退款前未校验已退款金额
- 缺少退款幂等控制

**解决方案**：

``` java
// 退款前校验
BigDecimal refundedAmount = refundOrderMapper.sumRefundedAmount(orderNo);
if (refundedAmount.compareTo(orderAmount) >= 0) {
    throw new BusinessException("订单已全额退款");
}

// 退款幂等控制
String refundKey = "REFUND:" + refundNo;
Boolean acquired = redis.setnx(refundKey, "1", 300);
if (!acquired) {
    throw new BusinessException("退款正在处理中");
}
```

**预防措施**：
- 退款前校验已退款金额
- 增加退款幂等控制
- 退款记录表增加唯一索引
